# hello 能力清单与工具列表（初稿，2026-11-18）

> 下一阶段的第一步（主人 2026-11-18）：先整理现在能用的能力 → 规范成统一的工具列表 → 逐个测试、补缺 → 再写技能 → 最后测技能、定触发。
> 本稿由四份只读盘点汇总而成（设备 / 耳朵 / mind 与数据库 / 模型与外部服务），对照的是 collector-0.5.07 和 2026-11-18 的服务器代码。
> 它更新并取代 [2026-11-14 的工具目录草稿](superpowers/specs/2026-11-14-llm-tools-catalog.md) 的「现状」部分；那份里的工具命名、R/A/C 分级、隐私和花费的约定继续沿用。

## 0. 先说结论

1. **能力其实不少，但几乎都是“事件驱动、写死在流程里”的**：耳朵（ear）没有任何“问一下就答”的接口，全靠机器人推上来的音频和画面驱动；mind 有 50 多个 HTTP 接口，但查询粒度固定，每次最多 24 小时。
2. **服务器不能动机器人**：转头、俯仰、追踪、表情、音量、切模式，都只能走机器人局域网上的 `/v1/control`（或 USB），服务器到机器人的三条连接上没有这些命令。这是“工具”层最大的缺口。
3. **“某人说过什么”查不了**：没有按说话人或关键词查原话的接口，`speech` 也没有对应索引。
4. **没有向量检索**：记忆相关性只靠两字词重合；可做 RAG 的现成单位已经有（记忆、对话纪要、片段、知识、人物笔记）。
5. **模型有几项强能力还没用上**：千问实时的函数调用（11-14 已验证，约 1 s 拿到参数）、联网搜索带来源（`enable_source`）、带图像的 omni 实时模型、TTS 的情绪标签。

### 1.3 mind 与数据

- **接口**：127.0.0.1:52740，带令牌，50 多个 GET / POST：情景、时间线、片段、每分钟画面、纪要、说过的话、标注、评分、花费、开关、模式、地点、记忆库（人、笔记、记忆、知识，版本化、只增不删）、运行日志（按时间 / 类别 / 链 / 账单查）。
- **模型调用**：情景 fusion、片段、纪要、每分钟画面、习惯记忆、每日记忆提取、注意力、台词、脱口秀、对话、探针；都走统一的花费账和每日 ¥20 上限。
- **数据库 `hello`**：原始数据（会话、说的话、声音、听悟、M12、照片、看图、Docking 每轮）、整理过的数据（每分钟包、情景、片段、模型调用、纪要和版本、每分钟画面、记忆、记忆库、对话轮次、台词、评分、开关、模式）、运行日志（按月分表，正文去重）。没有自动删除。
- **现成的整理能力**：每分钟情景、片段摘要、对话纪要、30 分钟话题时间线、每分钟画面总结、习惯记忆、每日记忆提取（带来源、敏感度、主人可审）、花费账单、断档检测、评分统计。
- **现成但没开接口的“好材料”**：`Records.window`（一段时间里所有原始记录）、`memory_extract.gather`（一天的材料按时间排好、去掉 hello 自己的声音）、`notes.topic_timeline`（话题时间线）。

## 3. 最大的几个缺口（建议的补法）

1. **服务器 → 机器人的命令线**：在 /mouth 上加一类经白名单过滤的命令（转头档位、追踪、表情、提示字、台词片段、音量不存版），机器人回执。这一条打通，2.5 和 2.6 的大部分工具就有了。
2. **耳朵的请求式接口**：一个只监听本机的小接口（或经 mind 转发），开出 `look_now`、`say`、`stop_speaking`、`who_is_here`、`set_length`、`web_search`，Docking 内部的现有函数直接包。
3. **mind 的查询接口**：`review_period`（超过 24 小时自动分天）、`speech_search`（加 `speech.speaker.name` 等索引）、`hello_said`、受限的 `db_query`；敏感度和“只对主人讲”的规则统一在这一层做。
4. **机器人状态上行**：遥测里的电量、温度、光照、姿态等，定期送一份精简版到服务器，`robot_status` 才有数据。
5. **RAG**：选一个向量模型，先给记忆、纪要、片段建可重建的向量表；费用进账、受每日上限约束。

## 4. 规范化与测试（下一步）

- **注册表**：每个工具一条记录（名字、用途、输入输出的 JSON Schema、在哪执行、延迟、费用、级别 R/A/C、前提开关和模式、状态），放在仓库里一份结构化文件，这份中文文档由它生成或与它对照，避免两边说法不一。
- **调用约定**：统一返回 `{ok, data, error, cost, ms, source}`；每次调用一条运行日志（类别 `call.tool.<名字>`），和触发它的那句话在同一条链上；R 类可缓存，A 类有频率上限，C 类只生成提议。
- **测试**：每个工具一个离线测试（假数据），加一个实机冒烟测试（真服务器、真机器人）；结果回填“状态”列。
- **然后**：写技能（回顾、解释自己、查证、深入研究……），再测技能、定触发（本地规则 / 千问函数调用 / 主人点名）。

## 5. 要主人定的

1. 第 3 节五个缺口的先后顺序。建议：③ mind 查询接口 → ② 耳朵请求式接口 → ① 服务器 → 机器人命令线（要刷机）→ ④ 状态上行 → ⑤ RAG。
2. 工具由谁来调：先只给技能（代码）调，还是同时开放给千问的函数调用？建议先只给技能，日志证明稳定后再放给千问。
3. `speech_search` 能查到谁的原话：只查主人，还是也查别人（别人的话按记忆库的“只对主人讲”规则）？
