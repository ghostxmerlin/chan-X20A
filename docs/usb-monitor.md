# USB 监视台（collector-0.4.82）

监视台地址仍为 `http://127.0.0.1:8787`。浏览器通过 SSE 接收 Mac 状态；Mac 的 Node 服务启动 Python 标准库桥接，按 `.private/stackchan-monitor.json` 中 `usb_serial`（缺省用 `device_id`）选择 USB Serial/JTAG，核对设备 HMAC 后订阅。USB 口名字随插口改变不影响匹配。无需安装 pyserial。

## 启停与刷机

`node web/monitor/service.mjs start|status|stop`，或原有 `scripts/open-stackchan-monitor.command`。绑定中的 `transport` 默认 `serial`，不自动回落 Wi-Fi。`address` 和 token 留存，方便将来恢复网络模式；token 只在本地服务和机器人之间使用，不传给浏览器。

刷机前执行 `stop` 并等待结束；它停止 Node 与 Python 桥接、释放串口。刷机仍按设备身份/活动分区检查、旧槽备份、仅应用分区写入、独立校验的流程进行。刷完后执行 `start`。不要同时运行另一个串口终端。关闭网页后约 1.5 秒停止订阅并释放串口，重新打开网页重新握手；控制请求不自动重放。

Python 桥接打开端口时不操作 DTR/RTS，禁用 HUPCL，申请 TIOCEXCL。实际无复位验证仅适用于已验证的这台 Mac/开发机器人，不能据此保证所有驱动组合。

## 数据与资源

- 首次连接或丢增量时读取全量；普通诊断以 1 Hz 采样，仅推送变化叶字段；每 30 秒补全量。
- 听觉和 ASR 事件独立检查、按各自序号去重；不会借事件到来刷新传感器有效期。M12 读取快照，不消费服务器上传队列。
- 相机从现有 JPEG 中取最新帧，最高 5 Hz；慢读时不累计历史画面。
- 一个 USB 发送者承载数据和脱敏日志。帧有类型、长度、CRC32；增量带 revision/base_revision，缺帧会停用控制并重新同步。
- Mac 每 2 秒续租，6 秒不续租停止遥测构造/图片输出。USB 单帧持续进展时最多允许 1 秒，无进展约 100 ms 退出；主机组帧期限 1.5 秒，固件小命令组帧仍为 250 ms。日志满队列即丢弃，业务任务不等待读者。
- USB worker 栈 12 KiB、JSON/序列化/图片及 16×384 字节日志存储在 PSRAM；USB RX 1024 / TX 2048 字节。会写 NVS 的共用控制 worker 使用 6 KiB 内部栈。
- 默认不启动两个 8 KiB HTTP 任务、UDP 发现和网络 SD 安装 worker。原始 PCM 环缩至电平计算所需的 25 块；耳朵自己的采集队列和网络上传保持不变。实际 RAM 收益须看同负载设备测量。

## 恢复旧网络监视

固件 menuconfig 的 `Collector monitor → Enable legacy HTTP and UDP network monitor`（`CONFIG_COLLECTOR_NETWORK_MONITOR=y`）可恢复原 8080、8081、8082 及网络资产安装 worker。重新构建、刷入后，把本机绑定配置 `transport` 设为 `http` 并重启监视服务。恢复时核对原 `address` 是否仍有效。USB 仍可用，但同一网页服务只选择一种传输。

网络关闭是监视入口关闭，不是关闭 Wi-Fi：听觉、视觉上传、TTS 嘴和 Mac 到 mind 的服务器连接仍正常联网。现有 SD 台词/眼睛不受影响；原 HTTP 资源安装脚本在默认构建中不可用，此次未加入 USB 大文件上传。

## 验证

### 网页短暂断连：系统日志突发（2026-11-12）

用户报告前端中断几秒后自动恢复。现场记录显示，系统任务日志批量到来后，网页 SSE 连接关闭；最后一名观看者离线约 1.5 秒后串口释放，浏览器约 3 秒自动重连，因而出现短暂停顿。Node 服务进程一直存活。

原因是本机服务在每条 USB 日志到来时都发送一份约 90 KB 的完整网页状态，忽略 `res.write()` 返回的背压信号；突发发送超过 256 KiB 阈值后主动 `destroy()` 连接。新增真实本地 TCP/SSE 回归，用含 400 条日志的实际 Monitor 缓存连续发送 30 次更新，旧实现稳定断开。修复后遇到背压等待 `drain`，期间合并通知，再读取最新快照；快照仍包含保留的各条日志，不累计旧快照队列。

修复前独立现场观察 75 秒，捕获 13:36:33 和 13:36:34 两次意外关闭，机器人 boot 未变化。修复后的 155 项 Node 测试全部通过。此次仅更新 Mac 网页服务，机器人继续运行 0.4.82，未刷机或重启机器人。现场对照在 `logs/usb-monitor-frontend-incident/`。

更新服务后连续观察 4 分钟，跨过 4 轮任务日志突发，共收到 1,796 条 SSE 消息、56 条任务日志；全程保持同一连接，意外关闭和离线消息均为 0，最大消息间隔 729 ms，机器人 boot 不变。观察结束后 API 仍在线且遥测新鲜，观看者恢复为原有的 1 个。此记录验证了该突发日志场景，尚未进行更长时间观察。

### 0.4.82：高负载重连修复（2026-11-12）

用户报告机器人本体界面卡住。调查期间网页服务存活，但相机、听觉同时开启后暂停/恢复监视出现持续串口超时。原始 USB 捕获仍有同一 boot 的新采集序号和眼睛渲染序号；未捕获 panic/backtrace。这只能定位当时的串口故障，不能排除用户此前观察到的实体界面停滞。

已证实的连接故障：0.4.81 对整帧设绝对 100 ms 期限；实际 `info` 回包声明 23,447 字节，只发出 15,616 字节就开始下一帧，状态和 JPEG 也截在 256 字节写入边界。主机在 `info` 完成前收到旧租约推送，又因 cache 尚未初始化触发额外 snapshot 请求。现在分别按持续进展/停读限制发送，主机等待完整握手后才处理推送或重同步。控制仍不自动重发。

- 新增发送进展/停读、慢速大帧和握手隔离回归均先复现失败再通过；Node 154 项通过，Python 408 项运行、404 通过、4 项跳过。固定 IDF 5.5.4 构建通过，独立只读审阅未发现阻塞问题。
- 旧 0.4.81 槽完整备份并独立核验；0.4.82 仅写 `ota_1 / 0x510000`，写后 verify 通过。应用 3,537,616 字节，SHA256 `920268103639172288195af23b41fe397fa6b1b65f0dd3353dcb994669acb97d`。
- 相机、听觉、v14 自然循环并发下，5 轮直接连接及采样通过，握手 564–1,291 ms；各轮正常读取阶段发送丢弃、音频采集错误和内存分配失败增量均为 0。重开端口时解析器曾丢弃旧残帧，随后成功取得新状态。
- 为恢复用户网页，结束独占串口探针并重新启动网页服务；随后连续 120 个约 1 Hz 样本全部在线、boot 不变、发送丢弃增量 0、听觉发送失败增量 0。眼睛渲染前进 298 帧、麦克风前进 6,009 块，内部 RAM 最低 71,267 字节。用户随后确认本体现在正常。
- 本体卡住是否与串口故障同因仍未证实；当前恢复正常不作为该根因已修复的结论。此次没有再次进行停读或物理拔线测试，也没有长期并发验收。

当前镜像在 `artifacts/collector-0.4.82-usb-progress/`，部署与并发证据在 `logs/usb-monitor-v0482/`；故障原始捕获和最后缓存状态在 `logs/usb-monitor-v0481/incident-*`。网页服务保持运行，相机、听觉和原眼睛款式已恢复。
