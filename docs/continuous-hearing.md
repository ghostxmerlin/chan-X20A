# 连续听觉

本体通过 Wi-Fi 直接连接 sherpa-onnx 后端。网页终端只负责配置和控制，不转发声音；关闭网页不结束已经开启的连续监听。

## 使用

1. 部署0.4.30及SD声音/眼睛资源后，打开 http://127.0.0.1:8787/ 。在“语音后端 · 配置与声纹”点击“使用本机现有后端”，或填写 ws/wss IPv4 地址与密钥。保存后待机，空密钥表示保留原值。
2. 说 **start**（Unit ASR工厂指令0x12）开始，或点击“开始连续监听”。说 **stop**（0x13）停止，也会取消本次声纹录入及该监听会话发起的台词/眼睛。开机默认待机。
3. 填写姓名，点击“录入五句话”。对着本体麦克风说五段自然语音，每段1–12秒，句间停顿；120秒未完成自动取消。录入期间不作情绪回应，完成后恢复原监听意图。
4. 同名资料默认保留；明确勾选“重新录入”才替换。后端先备份原声纹库，再原子保存。取消/断线/旧推理结果不能写入下一次录入。

**回应所有人，声纹仅显示身份。** 回应与录入使用独立于身份的 acoustic_band。known/unknown不改变同一段声学证据的触发条件。界面显示身份、最后转写、情绪、录入进度与连接错误；情绪标签是实验性分类，仅作互动参考。

情绪对应自 collector-0.4.56 起来自 `config/voice-emotions.json`：80 条台词每条恰好一个后端标签，回应时在该标签的全部台词中均匀随机、尽量不与上一次相同；眼睛沿用该台词的近似表情。2026-11-09 用户要求“全部语音都能对应进去”，因此 neutral / unknown 也有台词（各 21 / 19 条），原 13 条对应不变。

只处理完整的人声结束事件和非空文字，5秒以上旧结果不回应；至少间隔10秒，忙时丢弃不排队。自身播放及结束后1.2秒的采集带 self 标记，在语音切片时冻结，避免延迟推理把自己的台词当外部声音。collector-0.4.35 起 ASR next按原流程等待800ms后随机播放（open改为水平追踪），网页普通点播不增加等待；手动眼睛优先。

## 接口与资源

- `POST /v1/control`，共同字段 `target:"hearing"`，其余参数：`{op:"config",url,token}`、`{op:"listen",enabled}`、`{op:"enroll",name,replace}`、`{op:"cancel"}`。均需原配对 Bearer 与当前 `X-Boot-Id`；不自动重发。info/telemetry的hearing字段不包含token。
- 24kHz mono Opus / 60ms / 40kbps VBR / complexity0 / AUDIO；当前SDK不在该模式开启DTX。复用原24k双通道采集的mic通道，独立有界队列、编码和传输任务。Opus worker 使用32 KiB PSRAM栈、优先级4（低于麦克风采集7），运行时报告栈余量和编码/发送/轮询耗时。
- SEA1包头：magic4字节、uint32 LE序号、uint64 LE首样本设备微秒、一个Opus包。后端解码16k；丢包显式记录并切断VAD段，前滚不越过缺口，旧排队语音清除。
- 单任务驱动IDF原生WebSocket transport，回调同步执行；连接/握手共享2秒预算，小消息发送1秒预算、超过8 KiB的画面3秒预算，TCP_NODELAY避免小包等待；空轮询不阻塞，可读后用共享200ms预算接收完整消息。stop即刻失效会话并shutdown已建立socket。只接受IPv4，避免阻塞DNS绕过取消；wss仍验证系统证书。
- 不升级依赖或改分区。原首页120帧的32色索引由8位无损打包为5位，节省336480字节；全部897360个原索引的SHA一致。
- 后端沿用录音留存，不自动删除。SEA1头不写入Opus文件；文件保留24k输入率，事件采样索引仍以16k解码时间线计。

## 实现复核中的决定

- 保持原分区和40条声音，通过无损索引打包释放空间；若实现不符会影响旧首页，已用所有原像素哈希回归。
- 使用播放会话归属取消旧声音，手动播放为独立归属；若边界不符会出现旧回应，主机策略测试覆盖取消与新会话。
- 配置暂限IPv4；若后端仅提供域名，须补可取消DNS支持。现有后端已核实符合。
- 关闭IDF `transport_ws`日志标签：其错误分支会打印含鉴权的完整请求。保留监视状态中的通用错误；代价是减少底层日志细节。

## 机器人麦克风的轻声门槛（2026-11-09）

机器人麦克风已是满增益，底噪约 −43 dBFS（100 Hz 谐波嗡声），打字只高出底噪约 4–12 dB。后端对 `stackchan*` 来源单独放宽轻声标签（打字、键盘、叹气、呼吸、喘、吸鼻、咳嗽、清嗓、喷嚏）：非说话时高于底噪 5 dB、CED 概率 0.30 即报，其他种类和 Mac 来源仍为 15 dB / 0.40。audio 回执的 `sound_profile` 显示当前档位。依据与回放结果见[会话交接](session-handoff.md)。


## 0.4.84：音频发送积压（2026-11-12）

旧版在麦克风采集错误为0、服务端心跳正常时仍持续丢块。现场 TCP 抓包确认，固定 [IDF 5.5.4 的 WebSocket sender](https://github.com/espressif/esp-idf/blob/v5.5.4/components/tcp_transport/transport_ws.c) 把每个60 ms音频帧拆成8 B头和约318 B载荷两次写入；结合 TCP_NODELAY，每帧占用两个小 TCP 段，还要执行三次可写检查。当前 lwIP 发送缓存5760 B，对应可写低水位8个 pbuf；实际链路 RTT 上升时，更易触及可写门限；旧版实际发送吞吐不足，3秒采集队列随后溢出或过期。此前只减少 self 消息和延长到1秒，仍未消除音频帧本身的拆包。

修复在调用端把 RFC 6455 掩码头和载荷组成一个完整帧，一次传给原生 transport；部分写入继续推进偏移，不重发已写前缀、不修改输入音频。握手、接收、证书验证、取消和发送预算不变，没有扩大 lwIP 内部 RAM 缓存或增加任务。普通音频使用512 B临时栈空间，大消息最多约32 KiB临时 PSRAM。嘴/视觉共享此传输类；服务端协议与服务代码没有修改。

新增 `hearing.capture_queue`：`blocks/capacity/high_water/last_age_ms/overflow/stale/sequence_gaps`，用于区分发送积压、队列溢出、过期与采集序号缺口。既有 `dropped_blocks` 在溢出后遇到序号缺口时可能重复计数，不能直接乘20 ms当精确损失时长。验收同时看分类计数和服务端 `audio_gap`，不隐藏缺口。

发送预算仍受 IDF 原生阻塞写语义限制，不能声称严格的墙钟超时上限。有限队列也无法保证任意长的网络断开不丢声音。实机对照与部署证据见 `logs/hearing-loss-v0483/`、`logs/hearing-loss-v0484/`；持续验证结果记录在本节末尾。
