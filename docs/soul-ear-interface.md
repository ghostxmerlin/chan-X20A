# StackChan → soul 耳朵服务器：音频上行接口（草案）

状态：**草案 v0.1，2026-11-07，未提交，待用户审阅**。服务器侧（Claude）起草，ESP32 侧（codex-astra）实现。本文只定义“机器人把声音送到 soul 服务器”这一条链路；下发表情、动作等指令另行定义。

公开仓库约定：本文中的地址、端口、令牌都是占位符。实际值放在本机私有配置里，不写进仓库、日志或导出文件。

## 1. 目的和原则

soul 是宠物型陪伴机器人。“大脑”放在公网服务器上，因为她会离开家，手机时有时无；所以由**机器人直接推流到服务器**，不经 Android 中转。服务器上的“耳朵”负责切段、识别、认人、声音分类，再交给大脑。

- **传感器只报告，不决策。** 机器人不判断“是不是人声”“该不该传”，有声音就立刻送；安静时 Opus 的 DTX 包只有 1–3 字节，持续发送几乎不占流量。
- **单一采集者。** 推流必须复用 collector 现有的音频采集数据，不另开一套 codec 读取循环，不独占麦克风，不阻塞采集任务（见 [情绪宝宝计划](haro-next-plan.md) 的约束）。与 Android 观察台的 8081 拉流并存。
- **不伪造数据。** 丢包、环形缓冲溢出、重连都要显式体现（序号跳变、新分段），不静默补齐。
- **录音保留。** 服务器把每次连接收到的音频和元数据完整存档、不自动删除；机器人侧的断网补录见第 7 节。

## 2. 连接

- WebSocket 客户端，机器人主动连：`ws://<ear-host>:<ear-port>/?token=<device-token>`。令牌错误时服务器以关闭码 4401 断开。
- 首版为明文 WebSocket。令牌和音频都不加密，是已知限制，见第 11 节。
- 断线后自动重连，退避 1、2、4、8、16、30 秒（封顶 30 秒），连上后重置。每次连接在服务器上是一个独立的录音分段。
- 可选：连上后看前几次心跳的回执延迟；同一网络下跨境 TCP 有时落到慢路径（实测约 60 ms 与 210 ms 两档，每条连接固定），慢就断开重连，最多 3 次。

## 3. 握手：音频声明（上行文本帧，连接后第一条）

```json
{"type": "audio", "format": "opus", "sample_rate": 24000, "channels": 1, "frame_ms": 60,
 "source": "stackchan-<device_id>", "framing": "sea1",
 "device": {"device_id": "<device_id>", "boot_id": "<boot_id>", "firmware": "collector-x.y.z",
            "protocol": "soul-ear/1", "channel_roles": ["mic"]}}
```

| 字段 | 含义 |
| --- | --- |
| `format` | `opus`（推荐）或 `pcm16`（调试用，约 384 kbps @24 kHz，不建议走热点） |
| `sample_rate` | **编码器输入采样率**。机器人采集是 24 kHz，直接按 24 kHz 编码即可，不必在设备上重采样；服务器解码到 16 kHz（已在主机上验证，采样数精确对齐） |
| `channels` / `channel_roles` | 首版 1 声道 `mic`。喇叭开始有播放业务后，再加第二声道 `reference`（见第 11 节） |
| `frame_ms` | 每个 Opus 包的时长，建议 60（与小智一致，服务器已实测）；20、40 也可以 |
| `source` | 录音目录名会用它，必须稳定、可辨认 |
| `framing` | `sea1` 表示每个二进制帧带第 4 节的包头；省略则表示二进制帧是裸 Opus 包（Mac 测试客户端现在的做法） |
| `device` | 与 `/v1/info` 一致的身份字段；`boot_id` 变化即新分段 |

Opus 编码参数建议照搬小智 v2.5.2（StackChan 出厂固件）：码率自动、可变码率、DTX 开、复杂度 0、AUDIO 模式、不开 FEC。24 kHz 输入时自动码率实测约 25 kbps（说话为主），安静时接近 0。

## 4. 上行音频帧（二进制帧，一帧一个 Opus 包）

`framing: "sea1"` 时，每个 WebSocket 二进制消息 = 16 字节包头 + 一个完整 Opus 包。风格与 collector 的 `SCA1` 一致：

| 偏移 | 类型 | 内容 |
| --- | --- | --- |
| 0 | 4 bytes | ASCII `SEA1` |
| 4 | uint32 LE | 包序号，本次连接从 0 开始，每包 +1 |
| 8 | uint64 LE | 本包首样本的设备单调时间，微秒（与 `SCA1` 同一时钟） |
| 16 | bytes | Opus 包（长度 = 消息长度 − 16） |

- **每个采集周期都发，安静时也发**（DTX 包）。不要因为安静而跳过，否则服务器无法把采样位置对回时间。
- 发送队列积压时可以丢最旧的包（小智的做法是积压超过 2.4 秒丢最旧），但序号照常递增，服务器据此发现缺口、补等长静音并记一条缺口事件。
- 一个 WebSocket 消息只放一个包，不拆不拼。

## 5. 上行控制消息（文本帧）

| 消息 | 何时发 | 用途 |
| --- | --- | --- |
| `{"type":"self","sounding":true,"moving":false,"t_us":<设备时间>}` | 喇叭开始/停止播放、舵机开始/停止动作时，**立即**发 | 她自己出声或在动时，耳朵把这段时间的事件标上 `self`，满足“她发声时语音输入要屏蔽或标记”的硬性要求；由大脑决定信不信 |
| `{"type":"ping","id":n}` | 可选，每 2 秒 | 服务器回 `pong`，用于测往返时间 |

## 6. 下行：每 100 ms 一帧心跳（文本帧）

服务器每 100 ms 发一帧 `tick`，事件随心跳带下来，每秒不超过 10 帧：

```json
{"v":1,"type":"tick","seq":123,"t":<服务器毫秒>,"rx":<已收采样数@16k>,"rx_bytes":<已收字节>,
 "rx_idle_ms":40,"rx_gap_ms":60,"level_db":-38.2,"noise_db":-55.1,"speaking":false,"events":[...]}
```

事件类型：`hello`、`audio`（确认声明）、`speech`（开口/说完：是谁、说了什么、像不像人声）、`sound`（声音事件）、`pong`、`error`。完整字段见服务器代码头部说明。

机器人**必须持续读取**下行帧（否则 TCP 缓冲会反压上行），但现阶段**可以忽略内容**；不要让下行处理阻塞上行发送。

## 7. 断线、重启与离线（部分待定）

- 断线重连、`boot_id` 变化：服务器各自开新分段，旧分段完整保留。机器人不需要续接旧序号。
- **离线补录（待定）**：连不上服务器时，是否把同样的 `SEA1` 包写进 SD 卡、联网后用单独连接补传（声明里加 `"backfill": true` 和原始开始时间），由用户与 ESP32 侧决定。当前 collector 没有 SD 挂载；眼睛资源也计划放 SD 卡（[soul-eyes](soul-eyes.md)），两者需一起规划空间与写入。

## 8. 与现有 collector 的关系

- 推流读取 collector 已有的 24 kHz 采集块（每块 480 帧），从中取 `mic` 声道，按 `frame_ms` 攒够后编码发送；`SCA1` 的设备时间可直接换算成 `SEA1` 的首样本时间。
- 不改动 `/v1/audio` 的现有行为；Android 观察台与服务器推流同时工作时，二者都不得丢块。
- Opus 编码在 ESP32-S3 上的开销参考小智（复杂度 0，16 kHz）；24 kHz 输入的 CPU、PSRAM 需在本项目实测，并与动画、摄像头、遥控并发测试，主机测试不能替代。

## 9. 服务器现状（2026-11-07）与待实现

已支持：令牌、`audio` 声明、裸 Opus 包（任意帧长、任意编码采样率，统一解码到 16 kHz）、`pcm16`、`self` 消息、100 ms 心跳、每连接完整录音存档（`audio.opus` 原样保存 + 事件、心跳、客户端消息、元数据）。

待服务器侧实现（本文审定后）：`SEA1` 包头解析与缺口补静音、设备时间与服务器时间对齐记录、`device` 身份写入录音元数据、双声道（`mic` + `reference`）。

## 10. 验收

1. 连上服务器，声明被确认（下行 `audio` 事件）。
2. 连续推流 10 分钟：服务器录音时长与墙钟一致（误差 < 0.5 秒），序号无缺口；心跳间隔中位数约 100 ms。
3. 说几句话：下行出现 `speech` 事件，文字可读；服务器 `audio.opus` 可直接播放。
4. 断网 30 秒再恢复：自动重连，服务器出现新分段，旧分段完整。
5. 同时打开 Android 观察台：两路都不丢块，collector 原有验收项不退化。
6. 发 `self` 消息时，期间的事件带 `self.sounding=true`。

主机侧参考实现：soul 项目里的 Mac 测试客户端（`spikes/ear-server/mic_client.py`，不在本仓库），已用同样的 Opus 参数实测。
