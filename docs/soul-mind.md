# hello 的思考后端（mind）：讨论记录

状态：**讨论中，还没有设计文档，也没有开始实现**。本文整理 2026-11-09 晚间的讨论和实测。服务器侧由 Claude（Opus）负责。

标注约定：
- **用户定**：用户拍板的决定；
- **我的建议**：Claude 提出、用户还没否定的做法，可以推翻；
- **实测**：在服务器或录音上跑过的结果。

## 1. 名字

- 机器人叫 **hello**（用户定，暂定）。取自 HAL 9000 和高达的 Haro，三个音很像。
- 以后如果拿名字当唤醒词，要注意 hello 在日常说话里很常见，误唤醒会多。
- 思考后端的模块名暂定 **mind**，与 `server/ear/` 并列（我的建议）。

## 2. 目标

用户的原话是"基于视觉/听觉输入和一份更高级的转写结果，做情景识别"，要完整回答三个问题：**我是谁、我在哪、旁边的人在干什么**。

- **连续**：这些问题的答案在时间上不能出现空档。
- **动态**：输入没有变化时，降低推理频率。
- **这是思考后端，不是对话后端**：不和人对话。

## 4. 架构草案

以下都是我的建议，还没写成设计文档。

### 4.1 输入

- **耳朵**：现有 Opus 音频流产出的转写、声纹判断和声音事件。
- **眼睛**：M12 认人结果（谁、几点、把握多大，量很小），加上每分钟的照片。照片要带上拍摄时头的朝向，转头途中拍的照片不用。
- **身体**：Wi-Fi 名、是否在出声、是否在动。
- 眼睛和身体这两路，可以并进现有的耳朵连接，作为文本消息发送。这部分是固件工作，等接口写好后交给 codex。

### 4.2 情景条目

- **强力元素由规则每秒刷新，不用 LLM**，所以任何时刻都有答案。
- **主人在不在，人脸和声纹两路分开记**，各自记录最后一次出现的时间。两路矛盾本身就是信息：看到主人的脸，声纹却判成陌生人，多半是声纹还没用机身麦克风登记。
- **"有人"分三种**：认识的人、看到但不认识的脸、听到但没看到的声音。
- **陌生人也要跨分钟追踪**：给没认出的人存一个临时声纹，形成"陌生人 A"。

### 4.3 推理

- 大约一分钟一次。输入是上次的情景、强力元素、这一分钟新增的谈话和照片；输出是哪些条目变了，以及三个问题的回答。
- **跳过**：强力元素没变、也没有新的说话时，不调用 LLM。连续跳过时，间隔逐渐拉长，但有上限。长时间没人声、没人脸，本身也是证据（人可能走了），要在上限内主动复核一次。
- **照片**：和上一张差不多时，不交给模型。

### 4.4 时间轴

- 情景一段接一段，每段写明起止时间和变化原因。断线那段也记一笔"我听不见了"，恢复后先对账（过了多久、Wi-Fi 名变没变），再决定是接上一段还是开新的一段。
- 变化累积到一定程度，做一次回顾整理（每小时级别）。
- 全部存档，不删。

### 4.5 展示与验证

- **调试网页**：此刻三个问题的答案和把握度、各条目和它们的来源、时间轴、每次推理被什么触发、花了多少钱。
- **离线验证**：先用已有的录音回放（录音里只有耳朵这一半），再接实时数据。

### 4.6 不做

- 不对话；
- 不影响 hello 的行为；
- 不做叙事式续写。情景识别必须清醒，分清看到的、推断的和假设的，它是将来叙事层的输入，两者不共用一个提示。

## 5. 转写和模型选型（讨论中）

| 用途 | 当前倾向 | 状态 |
| --- | --- | --- |
| 谁在什么时候说话、是谁 | sherpa-onnx 离线说话人区分（pyannote 分段，几 MB）+ 现有 CAM++ 声纹和声纹库，在本服务器上算 | 我的建议，未实测 |
| 说了什么（更准的文字） | 听悟实时 | **实测效果差，见第 6 节**，待重新比较 |
| 对比候选 | gpt-4o-transcribe-diarize（aihubmix 上有）：最多可给 4 个人的 2–10 秒参考录音，直接标出名字 | 未实测 |
| 不用 | FunASR：和 sherpa-onnx 重复，还要占共用服务器的资源 | 我的建议 |
| 每分钟更新情景（照片一起看） | gpt-6-luna（$0.1 / $0.5 每百万 token；按列表价估算，每分钟一次一天也不到 $1） | 我的建议，未实测 |
| 每小时回顾整理 | gpt-6.1-terra（$1 / $5） | 我的建议 |

调研过的先例：Dey 的情境感知计算（身份、地点、活动、时间）、Endsley 的情境意识三层、StreamMind（事件闸门）、EM-LLM（按意外切分事件）、OM1（传感器转文字再融合，但每轮重写，没有持续存在的状态）、Generative Agents（记忆流加反思）、Graphiti/Zep（事实带有效期）、Frigate（有事件才让视觉模型描述）。结论是没有能整套拿来用的项目，借思想、自己写一个轻量实现。

## 6. 实测：听悟实时（2026-11-09 晚）

- **录音**：两段修正前的机器人录音，按 sherpa 声纹分数挑"最像主人"的部分。A 是 2 分 10 秒的多人交谈，B 是 80 秒、主人说得多。共约 3.5 分钟，花费约 5 分钱。
- **脚本和原始结果**：在本机 `.private/mind-tingwu-test/`（不提交），服务器上在 `~/soul-mind-test/`。用的是 hubmix 的听悟 key（`~/aidea/agent/.env`），没有复制出来。

结果：

1. **实时模式下，每句话出来时不带说话人编号**，只有文字、逐字时间和句子编号。
2. **结束任务后，最终结果里有说话人编号**（`paragraphs[].speakerId`），结束后约 10–20 秒就能拿到。B 段分出两个人，和 sherpa 的"像主人 / 不像主人"分段一致。
   - 结束实时任务的正确调用是：再调一次 `createTask`，带 `type: realtime` 和 `dataId`。`stopTask`、`endTask` 都不合法。
   - 取结果用 POST 加 `getTask`。
3. **漏字严重**：A 段 sherpa 有 22 段话，听悟只出了 5 个碎片；B 段只认出大约四分之一的字。
   - 音量放大 20 dB 后，多认出一些，但开头 9 秒全丢了。
   - 滤掉嗡嗡声、把音量拉平后，反而只剩两句。
   - 所以对这两段来说，单靠电平解释不了漏字。
4. **18 点以后的录音确实有修正**：安静时底噪从 −44 降到 −54…−56 dBFS，100 Hz 嗡嗡声低了 10–25 dB。但修正后几乎没有录到人说话（最后一段机器人录音结束在 19:26），所以还没能在修正后的声音上测试。
5. **附带发现 hubmix 的 bug（未修改）**：`server/agent/tingwu.py` 的 `query_task` 用 GET 查结果，DashScope 返回 400"不支持 GET"，应改为 POST 加 `getTask`。

## 7. 下一步（明早）
