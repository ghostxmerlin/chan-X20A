# mind 第 1 阶段：模型融合、“此刻”与情景段、设置、标注与重跑 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 每分钟让 luna 在规则底稿之上写出一份全面、有证据、有把握档位的情景；网页主视图改成“此刻”卡片加今天的情景段（分钟明细折叠），并能在网页上改设置、一键打点、给分钟标对错、换提示版本重跑一分钟。

**Architecture:** 在第 0 阶段的 `server/mind/` 上加：设置改存数据库并带版本（`settings_store.py`）；提示与输入渲染（`prompts.py`）；输出校验（`validate.py`）；模型调用、运行记录、闸门与沿用（`fusion.py`、`llm.py`）；规则切段与段总结（`segments.py`）；接口加只写这几张 mind 表的 POST。Mac 监控页代理放行这些 POST，页面重做。照片、快照、记忆层不在本阶段。

**Tech Stack:** Python 3.11 标准库 + pymongo；Node 24 标准库；aihubmix OpenAI 兼容 `/chat/completions`，`response_format: json_schema` 严格模式（第 0 阶段探测：luna/terra 5/5 合格）。

**Spec:** `docs/superpowers/specs/2026-11-10-mind-design.md`（正文 3.3、3.6、4.1、4.2、4.5、5、7、9.1–9.3，加开头“修订”和“已定事项”）。

**相对 spec 第 11 节的调整（用户 2026-11-10 同意“阶段1吧”）：** 情景段和“此刻”视图从第 3 阶段提前到本阶段（段的总结用 luna，不用 terra）；闸门做最小版；重跑只做“单分钟、换提示版本或模型”，范围重跑和泳道对比留到第 4 阶段。原因：用户看了第 0 阶段页面“没什么感觉”，单分钟切片读不出情景，需要连续的段和一句“此刻”。

## Global Constraints

- 原始表只读；mind 只写 `mind_*` 表；什么都不删，重算出新版本。所有 mind 表带 `lane`；真实运行 `"live"`，重跑写 `"rerun"`，重跑永远不写 `live`。
- **语言内容发给模型，但情景要全面，语言不是唯一重点**（用户定）：输出按维度 `people / activity / sound_scene / vision / self / time_place / topic / contradiction` 写；活动类条目在本分钟有非语言证据时必须引用它。
- **把握要校准，不要处处“不明”**：提示要求“在证据范围内说出最可能的情况并标把握；只有确实没有证据时才写不知道”（第 0 阶段原型的教训）。
- 规则算出的主人状态是底稿，模型不能改它；模型另给 `owner_view`，与规则不一致时记 `rule_conflict`。
- 模型只用 `gpt-6-luna`（默认）或 `gpt-6.1-terra`（设置或重跑时选）；严格 `json_schema`；单次超时 90 秒；失败重试 1 次（带校验错误），再失败本分钟按“沿用”并记失败。
- 每日花费上限默认 `1.0` 美元（设置项），超过后当天只每 30 分钟调一次。价格表沿用 `probe.PRICES`。
- 自动融合只做最近 `fusion.max_age_min = 60` 分钟内的分钟；更早的历史只在命令行 `--rebuild … --fusion` 时调模型。
- 密钥、真实称呼不进仓库；设置的真实内容只在服务器数据库 `mind_settings`；仓库示例用占位名。
- 接口仍只监听服务器 `127.0.0.1:52740`、要 token；POST 只接受 `application/json`、正文 ≤ 16 KB；Mac 代理只放行列出的路径，POST 需同源（与 `/api/control` 相同的检查）。
- 页面遵守监控页 CSP：不内联脚本，不在 markup 里写 `style=`（用 `paint()`）。

## Review Focus

1. **模型引用不存在的代号、或“看到/听到”却没有本分钟证据**：期望去掉无效代号并计数，“看到/听到”降为“推断”。测试在 Task 3。
2. **aihubmix 超时、限流、返回非 JSON**：时间轴不断，本分钟记“沿用”（或第一分钟“仅规则”）并标失败，连续失败退避 1→2→5→10 分钟。测试在 Task 4。
3. **房间一直没变化**：不每分钟重复调用、措辞不抖；但主人状态换档、感官从关到开时必须立刻调用。测试在 Task 4。
4. **网页上保存了不合法的设置**（主人名字空、名字过长、文本超长、类型错）：拒绝并说明，旧版本继续生效。测试在 Task 1、Task 7。
5. **重跑写进了真实时间轴**：期望只写 `rerun` 泳道，`live` 的记录数和内容不变。测试在 Task 7。

### Task 3: 输出校验与条目合并

**Files:**
- Create: `server/mind/validate.py`
- Test: `tests/test_mind_validate.py`

**Interfaces:**
- Consumes: `prompts.SCENE_SCHEMA`、`prompts.RULE_CODES`、分钟包 `codes`、strong。
- Produces: `validate.apply(out: dict, prev_entries: list, pkg: dict, strong: dict, minute_ms: int) -> tuple[dict, dict]`，返回 `(scene, checks)`：
  - `scene = {"who_am_i", "where_am_i", "people_doing", "owner_view", "entries": [...], "changes", "summary", "want_to_know"}`；每个条目加 `since`（新增时 = minute_ms，keep/update 继承）和 `last_evidence`（本分钟有有效代号时 = minute_ms，否则继承）。
  - 规则：
    1. 证据代号只保留 `pkg["codes"]` 里的、`RULE_CODES` 里的；去掉的计入 `checks.invalid_refs`。
    2. `basis ∈ {seen, heard}` 而去掉无效代号后没有本分钟的包内代号（只有规则代号也不算）→ 改为 `inferred`，计入 `checks.downgraded`。
    3. `keep`：key 在上一分钟里就原样沿用上一分钟的条目（忽略模型这次写的正文）；不在就当 `add`。`update`：把握比上一分钟高，但本分钟没有有效包内代号 → 维持上一分钟的把握，计入 `checks.raise_blocked`。`end`：从结果中去掉，记入 `checks.ended`。上一分钟有、这次没提到的 key → 保留，计入 `checks.omitted`。
    4. `rule_conflict`：规则状态映射 `seen|just_left|likely_present → present`、`likely_absent → absent`、`unknown|sensors_off → unknown`；与 `owner_view` 不同且两者都不是 unknown → `checks.rule_conflict = true`。
    5. `language_only`：dimension ∈ {people, activity} 的条目中，证据全是 `s*`/`t*` 代号、而本分钟存在 `a*` 或 `v*` 代号的条目数 / 这类条目总数（无则 0）→ `checks.language_only`。
    6. `summary` 截到 20 字；每个 `text` 截到 200 字；条目最多 20 条。

    - 成功 → `validate.apply` → `put_scene(source="model")`；carry → `put_scene(source="carried", carried_from=上一条的 minute)`，scene 原样复制。
    - 每次调用都 `put_run`（失败也写）。返回写入的情景记录。`force_prompt/force_model` 给重跑用（Task 7），这时跳过闸门、预算与退避。
