## 0. 先说结论

1. **第 1 期只建库。** 新建五个集合：
   - 人物卡；
   - 人物条目（性格等，一条一条加）；
   - 记忆（一件件发生过、被告诉过的事）；
   - 知识（从记忆整理出来的认识）；
   - 声纹标注（第 1 期只建空集合，第 4 期才开始写）。

   都只追加版本，带索引。再加一组读写接口和调试页上的一块"库"视图，主人可以手工录入、改、停用、看历史。第 1 期**不读进任何提示，不接任何模式，不改耳朵，不花一分钱**。
2. **按"这条内容说的是什么"来分**（第 2 节）：
   - 说的是某一个人：进人物库。他是谁、怎么认、怎么叫、怎么对待、他是什么样的人。
   - 一件件发生过、被告诉过、被听到的事，带时间和出处：进**记忆**。事件、某次说起的工作情况、陪伴中听到的心事，都在这里。
   - 从许多件事里提取、融合、整理出来的认识：进**知识**。地点、工作背景、长期任务的现状、生活中的事、行话的意思、hello 自己的毛病，都在这里。
   - 用户说的"长期记忆"由记忆和知识这两层共同承担。
   - hello 该怎么做事的规矩，留在设置里。
3. **主人写初版，以后靠数据融合。** 人物条目和知识条目的每个版本都记下来历：是主人写的，还是融合出来的；融合时用了哪些输入，对照的是主人的哪一版。主人的原版永远留着，页面上可以并排对照。这次不设计怎么融合。
4. **声纹改为事后标注。** 不做无监督聚类。第 4 期做"每日回顾"页：主人回听服务器上的 Opus 录音，顺便标出每句是谁说的。标注只追加，以后用来给每个人做声纹、并拿没参与做声纹的日子检验认人效果。
5. **读取速度不是问题。** 审计在 28 个真实点击时刻重测：读一次上下文中位 27.6 ms，记忆查询只占 0.8 ms，慢在会话查询（第 1.6 节）。第 1 版的"随手卡"已去掉。
6. **现有的日常记忆引擎保留不动。** `mind_memories` 继续只管自动归纳的 `habit` / `routine`。它的 `reconcile` 会把这一轮统计里没出现的自动条目改成"待复核"（`server/mind/memory.py:188-197`），所以新内容另起集合。两边在接口和页面上并排显示，不合并。
7. **感官关着，就没有付费任务在跑。** 第 1 到第 4 期全部免费。第 5 期的整理和融合要花钱：只在感官开着时跑，前一天的内容第二天感官打开后再整理。关感官这个动作本身永远不触发付费任务（第 7 节）。
8. **按意思检索：第 1 期不要，第 5 期要。** 知识是从全部数据里融合出来的，融合时要先找到"意思相同的已有条目"，否则会重复。所以第 5 期开始给记忆和知识存文本向量，优先用服务器本机的小模型，进程里暴力算，不加向量数据库，也不要图数据库（第 8 节）。

### 1.2 身份：现在怎么认人

- **声纹库**是耳朵旁边的一个 `speakers.npz` 文件，耳朵启动时读一次（`server/ear/ear_server.py:156-159`）。现在 2 条，都是主人的，每条 192 维【实测】。
- **每句话的判断**：余弦 ≥0.6 记 `known`，≥0.4 记 `unsure`，否则 `unknown`（默认值在 `server/ear/ear_server.py:263`，判断在 `:460-467`）。
- **比例**【实测】：`known` 320 句（7.7%，只有主人），`unsure` 1320 句（32.0%），`unknown` 2490 句（60.3%）。
- **声纹向量算了但没存**：`server/ear/ear_server.py:631` 算出，`:646` 打分，`speech_doc` 只存名字和分数（`server/ear/hello_db.py:35-42`）。
- **审计的抽样实测**（907 句，从保留的录音重算）：
  - 从录音重算很准。和库里存的分数相比，差值中位 0.0002，"最像谁"100% 一致。全量重算约 5 分钟计算，加约 3.5 分钟解码。
  - 但没有标注时分不开人。主人的两条声纹之间余弦只有 0.348，最可能是两次录入的录音条件不同；拿听悟编号当参照，区分度 AUC 只有 0.70；层次聚类在四个门限下都不像样。
  - 一句是按停顿切出来的一段，最长 20 秒，常常混着几个人的话。
  - 这些都说明：要靠**人标过的句子**来做声纹和检验，不能靠无监督聚类。这正是用户回答第 4 条的做法。
- **"加入声纹库"不能从外面写文件。** 耳朵只在启动时读文件，之后录入和删除都拿内存里那份整份重写（`server/ear/ear_server.py:203-207`，`server/ear/hearing_protocol.py:130-147`）。别的进程写进去的条目会被盖掉。要加入，得给耳朵加一条消息。
- **人脸库在 M12 上**，服务器只收到名字和跟踪编号，没有人脸向量【实测】。人脸登记的命令是 M12 的 `learn`，现在只能经 USB 页面调用（模式设计 5.3 节）。
- **设置里的人**：`owner`（显示名、每天轮换的称呼、声纹名、人脸名）和 `people` 列表（`server/mind/settings.py:14-15`）。第 4 版【实测】：主人 2 个声纹名、1 个人脸名、4 个称呼；`people` 为空。
  - 主人的称呼不是普通别名：`owner_name()` 每天从中轮换一个当显示名（`server/mind/settings.py:83-91`）。
- **读设置里的人的地方**（以后迁移时都要改）：
  - `subject()` 把主人记成 `owner`，别人记成 `person:` 加显示名的哈希（`server/mind/speech_context.py:16-23`），记忆提取也用它；
  - 每分钟判断"主人在不在"的规则（`server/mind/strong.py:90-91`、`:100-148`）；
  - 提示里的称呼：`server/mind/prompts.py:93-99`、`server/mind/notes.py:120-122`、`server/mind/eye.py:66`；
  - 记忆 worker 的窗口指纹里也有 `owner` 和 `people`（`server/mind/memory_worker.py:179-180`），一改人就会让窗口重算。

## 2. 各库装什么

### 2.1 分界：按这条内容说的是什么【我定，按用户的归法】

按顺序问，第一个"是"就停：

1. **它是一条让 hello 照着做的规矩吗？**（避开的话题、角色、方言、主人说出口的口味原则）→ **设置**。脱口秀设计已写明"主人定的原则优先"。
2. **它说的是某一个人本身吗？**（他是谁、怎么认出他、怎么叫他、怎么对待他、他是什么样的人、他做什么、和主人什么关系）→ **人物库**。
3. **它是一件具体的事吗？**（某个时间发生的、某次被告诉的、某次听到的，能指出出处）→ **记忆**。
4. **它是从许多件事里整理出来的认识吗？**（这个地方是什么、这项工作的背景、这件长期在做的事现在怎样、生活里的什么规律、这个词什么意思、hello 哪里容易坏）→ **知识**。

一句话：**记忆是一件件的事，知识是整理过的结论。** 知识每一条都应当能说出"它是从哪些记忆来的"。主人手写的知识条目是例外：它没有记忆可指，来历就是"主人写的"。

"谁写的、怎么得来的"不决定放哪，另有 `origin` 和 `source` 字段记来历。

### 2.2 难分的情况

| 东西 | 放哪 | 说明 |
| --- | --- | --- |
| 某人的性格、做什么的、和主人什么关系 | 人物库，人物条目 | 主人写初版，以后融合；每个版本带来历 |
| 给某人起的外号 | 人物卡的 `aliases` | 是"怎么叫他" |
| 某人"不能拿来开玩笑" | 人物卡的 `treatment` | 主人定 |
| 某人那天说的一件事 | 记忆 `event`，`subjects` 指向他 | 人物页上汇总显示，不重复存 |
| 上周六去爬了某座山 | 记忆 `event` | 一件事 |
| 那座山、登山团体是怎么回事 | 知识 `place` / `commitment` | 整理出的认识，`derived_from` 指向那些登山的事 |
| 主人某天讲起的工作情况 | 记忆 `told` | 一次讲述 |
| 主人的工作背景 | 知识 `work` | 从多次讲述和纪要里整理；`environment` 文本是主人写的第一版 |
| 辅导孩子这件长期的事 | 知识 `commitment` 记现状；每次进展是记忆 `event`，用 `topics` 指向它 | 2.3 |
| 陪伴中听到的心事 | 记忆 `feeling` | 用户定：进长期记忆，全局可用 |
| 从许多次心事里看出的情绪规律 | 知识 `life`，或这个人的人物条目 | 以后融合 |
| 同事的习惯、时段规律（自动归纳） | 现有 `mind_memories` | 不动；以后融合时可以当输入 |
| 办公室行话的意思、常被听成什么 | 知识 `term` | 行话第一次闹的笑话是记忆 |
| 给东西起的代称 | 知识 `term` 的 `aliases` | |
| hello 的零件和毛病 | 知识 `self` | hello 哪天刷了几次、哪次断线是记忆 `self_event`（第 2 期） |
| 主人的笑话口味 | 不在这几个库里 | 打分在 `owner_signals`，口味说明在 `say_taste`，归脱口秀设计 |
| 谁说了哪句话（声纹标注） | `voice_labels` | 是主人对原始录音的标注，不是记忆也不是知识 |
| 情绪锚点、影子预测 | 不在这几个库里 | 归遥控方案 |

### 2.3 长期任务

用户举的例子（辅导孩子、登山团体）分两层存【我定】：

- 一条知识 `commitment` 记这件事本身：涉及谁、在哪、多久一次、从什么时候开始、现在进行到哪、还在不在做。它会随着新的事一版一版改写。
- 每次进展记成一条记忆 `event`，`topics` 指向这条知识。

这样"主人生活里长期在做的事"和"hello 参与、要记住进度的事"都放得下，只是后一种挂的记忆多。

### 2.4 和 mind 设计、现有引擎的关系

mind 设计 6.2 节把记忆分了层（`docs/superpowers/specs/2026-11-10-mind-design.md`）：

- 第 3 层"每天的日志"就是现在的情景段和纪要，不改。新的 `memory_items` 是从日志里挑出来、值得长期留的一件件事，加上主人亲口告诉的事。
- 第 4 层"事实"（跨天的规律，关于人、地点的认识，带有效期）由三处承担：
  - 自动归纳的日常规律在 `mind_memories`（现有）；
  - 关于人的在 `people_notes`；
  - 其余的在 `knowledge_items`。
- 现有的 `known` 状态对应新集合的 `active`。

不另起第三套设计，也不合并现有引擎。

## 3. 第 1 期：库本身

### 3.1 五个新集合

集合名都避开已有的名字：设置里有 `people`，看图结果里也有 `people`，所以人物集合叫 `people_cards`。

所有集合共用这些规则：

- 只追加。改一条就写一个新版本，带 `actor`、`reason`、`changed_at`、`supersedes`，旧版本不动。
- 用 `(编号, version)` 唯一索引防并发写。版本冲突返回 409，和现有的 `MemoryConflict` 一样。服务器是单机，没有事务，靠这个就够。
- 停用、退场、合并都是新版本的状态，**不删**。
- 没有任何 TTL 索引，没有任何自动清理任务，没有删除接口。

#### `people_cards`：一人一卡

```
{
  person_id: "p_<随机>",            // 永远不变；主人固定为 "owner"
  version, status: "proposed" | "confirmed" | "merged" | "retired",
  kind: "owner" | "regular" | "visitor" | "family" | "unknown",
  display: "<主人给的称呼>",
  aliases: [...],                     // 别人对他的叫法、外号
  owner_rotation: false,              // 只有主人那张卡可以为 true，见 3.4
  links: { voice_names: [...],        // speakers.npz 里的名字
           face_names: [...],         // M12 人脸库里的名字
           legacy_ids: [...] },       // 以前的 "person:<哈希>"，迁移用
  treatment: { tease: "ok" | "words_only" | "never",
               quote: "ok" | "gist" | "no" },
  scope_ids: ["office"],              // 在哪些场景出现
  merged_into: null,
  source: { kind: "owner" | "settings_import" | "m12_name", ref },
  actor, reason, changed_at, supersedes
}
```

- 索引：`(person_id, version)` 唯一；`(status, changed_at)`；`links.voice_names`、`links.face_names`、`aliases` 三个多键索引，以后按名字反查人用。
- `treatment` 的默认值【我定，和脱口秀设计对齐】：身份不明的人 `tease = "words_only"`，只接他说的内容，不评价他本人；`quote = "gist"`，可以提他说的意思，不逐字长段复述。
- 卡上没有长文本字段。关于这个人的内容都进下一张表。

#### `people_notes`：关于一个人的条目，一条一条加

```
{
  note_id: "n_<随机>", version, person_id,
  kind: "trait" | "fact" | "preference" | "boundary" | "relation",
        // 性格 / 稳定事实（做什么的）/ 喜好 / 不能碰的 / 和主人的关系
  text: "<≤200 字>",
  status: "active" | "candidate" | "disabled" | "retired",
  scope_id,
  // ---- 来历（见 3.3）----
  origin: "owner" | "fused" | "import",
  owner_original: { note_id, version } | null,
  derived_from: [{ c: "<集合名>", id, version? }],
  fusion: { run_id, method, model, prompt_version, at } | null,
  actor, reason, changed_at, supersedes
}
```

- 索引：`(note_id, version)` 唯一；`(person_id, kind, changed_at)`；`(origin, changed_at)`。
- 第 1 期只有主人能写，`origin = "owner"`，状态直接 `active`。
- 现有自动提取的规矩"不记录对人的性格、疾病、能力猜测"（`server/mind/memory_worker.py:25`）**只管现有的日常记忆 worker**。人物条目由主人写初版，以后由融合产出新版本（用户回答第 3 条），不受它限制。

#### `memory_items`：一件件的记忆

```
{
  memory_id: "e_<随机>", version, scope_id,
  kind: "event" | "told" | "feeling",
        // 发生过的事 / 被告诉的一段情况 / 陪伴中听到的心事
        // 第 2 期加 self_event；种类是可以加的词表，加一种不需要迁移
  title: "<≤30 字>", statement: "<≤300 字>",
  subjects: ["owner" | "p_…" | "hello" | "room"],
  topics: ["k_…"],                    // 和哪些知识条目有关（地点、长期任务、工作……）
  when: { type: "point" | "span", start_ms, end_ms },
  source: { kind: "owner" | "conversation" | "companion" | "rule" | "extracted",
            refs: [{c: "conversations" | "speech" | "utterances" | "say_rounds" | "owner_signals" | "sessions", id}] },
  status: "active" | "candidate" | "retired" | "disabled",
  actor, reason, changed_at, supersedes
}
```

- 索引：`(memory_id, version)` 唯一；`(scope_id, kind, when.start_ms)`；`subjects` 多键；`topics` 多键。按人、按时间、按种类、按长期任务都能直接取。
- 没有"能在哪里提起"的限制：用户回答第 2 条，情绪内容全局可用。各模式自己的规矩（比如围观不读）照旧在模式里管。
- `refs` 能指向 `say_rounds`（脱口秀一轮，用 `{rid, line}`）。
- 使用次数、冷却**不放在版本里**。以后要用时另起一个只追加的 `memory_uses`（哪一轮、给了哪几条、用了哪条），这是现有引擎的做法（`server/mind/memory.py:182-191` 的注释）。第 1 期不建它。

#### `knowledge_items`：整理出来的知识

```
{
  kid: "k_<随机>", version, scope_ids: ["office"],
  kind: "place" | "work" | "commitment" | "life" | "term" | "self" | "other",
        // 地点 / 工作背景、项目 / 长期任务 / 生活中的事 / 行话 / hello 自己 / 其他
  name: "<标题或标准写法>", aliases: [...],
  heard_as: [...],                    // term 用：常被转写成的样子
  statement: "<≤400 字>",
  subjects: ["owner" | "p_…" | "hello"],
  when: { valid_from, valid_to },     // valid_to 为空表示仍然成立；矛盾时关旧开新
  status: "active" | "candidate" | "stale" | "disabled",
  // ---- 来历（见 3.3）----
  origin: "owner" | "fused" | "import",
  owner_original: { kid, version } | null,
  derived_from: [{ c: "memory_items" | "people_notes" | "mind_memories" | "conversations" | "speech", id, version? }],
  fusion: { run_id, method, model, prompt_version, at } | null,
  actor, reason, changed_at, supersedes
}
```

- 索引：`(kid, version)` 唯一；`(kind, changed_at)`；`name`、`aliases`、`heard_as`、`subjects` 多键。
- 第 1 期主人可以直接写，例如把 `environment` 里的内容抄成几条 `work`，或写一条"登山团体"的 `commitment`。

#### `voice_labels`：谁说了哪句话（第 1 期只建集合）

```
{
  lid: "l_<随机>", at, actor: "owner",
  target: { session, speech_id,        // 指向 speech 的 (session, id)
            pos: [start, end],         // 采样位置，可以直接回到录音
            tingwu_n: null },          // 如果是按听悟段落标的
  person_id | null,
  verdict: "is" | "not" | "several" | "hello_self" | "noise" | "unsure",
  via: "single" | "group",             // 一句一句标，还是一组一起标
  group: { kind: "tingwu_speaker" | "run", key } | null,
  review_day: "2026-11-12",
  page_version
}
```

- 索引：`lid` 唯一；`(target.session, target.speech_id, at)`；`(person_id, at)`；`review_day`。
- 只追加。同一句话标了好几次，以最后一条为准，旧的不删。
- 一组一起标（比如"这一段里听悟的 2 号都是某人"）时，**展开成每句一条**，`group` 只记当时是怎么一起标的。这样以后换切句方法、换模型，主人的标注仍然指向具体的句子和录音位置，不会失去所指。
- 不放进 `owner_signals`【我定】。`owner_signals` 是主人对 hello 说的话的反馈；声纹标注是对原始录音的标注，一天可能几百条，分开放两边都好查。`mind_labels` 不动。

| 集合 | 第 1 期谁写 | 第 1 期谁读 | 以后谁写 | 以后谁读 |
| --- | --- | --- | --- | --- |
| `people_cards` | 主人（页面） | 页面 | 第 2 期导入设置里的主人、M12 名字（只提议）；设置模式录人脸后（模式设计 S7） | mind 的 `subject()`、主人在场规则、各提示的称呼（第 3 期） |

### 3.3 来历：融合版怎么追溯、怎么和主人原版对照

用户回答第 3 条："初始的我写，之后靠我们将来收集的全部数据来融合。"这次只把存储准备好，不设计融合。

- **主人的版本永远留着。** 融合产出的是同一条目的新版本（`supersedes` 指向上一版），或者是一条新条目。主人写的那个版本文档不改。
- **每个融合版都能说清来历**：
  - `origin = "fused"`；
  - `fusion` 记哪次运行（`run_id` 对应 `mind_runs`，费用可查）、什么方法、什么模型、哪版提示；
  - `derived_from` 列出用到的记忆、纪要、句子，带版本号，以后能重放；
  - `owner_original` 指向它对照的主人原版。如果这一条是融合新提出的、主人从没写过，就为空。
- **页面上的对照**：每条显示"主人原版"和"当前版"两栏，中间是历次融合的版本列表。主人可以点"回到我的版本"，等于追加一个内容和原版相同、`origin = "owner"` 的新版本。
- **主人后来亲手改**：照样追加，`origin = "owner"`。以后的融合以它为新的 `owner_original`。
- **融合版立刻生效**（用户回答第 6 条）：写入时就是 `active`，成为当前版本，不等主人点头。页面上把每次变化标出来，主人想看就看，不满意就点"回到我的版本"。

- 第 2 期从设置导入一次主人卡，标 `owner_rotation: true`，四个称呼放进 `aliases`，并注明"每天轮换一个当显示名"。

### 3.5 读写接口和调试页（第 1 期）

**接口**挂在现有的 mind 接口上（`server/mind/api.py`），都用 `/db/` 开头，免得和现有的 `/memories`、`/memory/history` 混在一起。鉴权沿用现有的令牌。

| 接口 | 做什么 |
| --- | --- |
| `GET /db/overview` | 五个新集合各有几条、各种状态和来历各几条；旁边列出现有来源的数字：设置里的声纹名、人脸名、`mind_memories` 的条数 |
| `GET /db/people` | 人物列表，每人最新版本加条目数 |
| `GET /db/person?id=` | 一张卡的全部版本、他的全部条目、`subjects` 里有他的记忆和知识（汇总视图） |
| `GET /db/memories?kind=&person=&topic=&from=&to=&q=` | 记忆列表；`q` 只在标题和内容里做字符串匹配 |
| `GET /db/knowledge?kind=&person=&q=` | 知识列表 |
| `GET /db/item?c=&id=` | 任意一条的全部版本；人物条目和知识条目附主人原版对照 |
| `POST /db/person`、`/db/person/note`、`/db/memory`、`/db/knowledge` | 新建或追加一个版本；带 `expected_version`，对不上返回 409 |

- 没有删除接口。列表默认每页 20 条。返回里不带录音或画面，只带引用。
- 调试页经 Mac 上的监控服务转发 mind 接口，转发白名单要加上这些路径（`web/monitor/mind.mjs:10-11`，`web/monitor/server.mjs:53`、`:83`）。

**调试页**：在现有 mind 页面（`web/monitor/public/mind.html`）加一块"库"。

- 顶部一行数字（来自 `/db/overview`），包括声纹标注的条数（第 1 期是 0）。
- 五个标签：人物、记忆、知识、现有日常记忆、声纹标注。"现有日常记忆"就是现在"长期认识与更新历史"那一栏，挪过来并排显示。
- **人物**：列表；点开看卡片、条目、和他有关的记忆和知识、每次修改的历史；可以加人、加条目、改对待方式、停用。
- **记忆**：按种类和时间列；可以按人、按知识条目筛；每条显示来源。
- **知识**：按种类列；长期任务点开看它下面的记忆；每条显示来历和主人原版对照。
- 每条都有"历史"按钮，显示谁在什么时候改了什么。
- 页面上写明：这些内容只在服务器数据库里，不进仓库；第 1 期没有任何提示在读它们。

### 3.6 保留和删除

- **录音永不自动删除。** 耳朵的录音目录、`speech`、`vision`、`frames` 这些原始记录，本设计任何一期都不删、不改、不搬。
- 新集合只追加。"停用""退场""合并"都是新版本，旧版本留着。
- **没有删除的接口，也没有删除的流程。** 有人要求"忘掉我"，由主人手动维护数据库（用户回答第 5 条）。本设计不为它做任何功能。主人能在页面上做的，最多是把这个人的卡标成 `retired`、把条目标成 `disabled`，让它们不再进任何提示。
- 以后会有可以重算的派生物（文本向量、每句话的声纹向量、"这句话是谁说的"的缓存）。它们能从原始记录和标注重新算出，换模型时可以整批重建，不算删除记录。

### 3.7 隐私

仓库是公开的，hello 在办公室里，周围的人没有被一一问过。用户已定：陪同事暂时不需要本人同意。调试阶段先求通，下面这几条是不增加复杂度的底线：

- **仓库里没有任何人的数据。** 不放种子数据文件，不放导出文件。测试和示例只用"人物甲""地点乙"这类占位。提交前用 `git grep` 查一遍设置里出现过的名字。
- **内容只在服务器数据库里。** 接口只在服务器本机监听（`server/mind/api.py` 的 `serve()` 默认回环地址），经监控服务加令牌访问。日志里只打编号和条数，不打条目的文字。
- **每日回顾页放出的声音**（第 4 期）由服务器从录音里现切现发，Mac 上不落文件。
- **围观模式**：不读这些库，不录入访客的脸（用户定："都存，先不登记"）。录音录像照常全部保留。
- 人物卡 `retired` 之后，他的条目不再进任何提示。
- 本文不写数据库的确切版本号和服务器规格，只说"单机社区版"。

### 3.8 第 1 期能试什么、怎么算失败

**能试：**

- 打开调试页的"库"，加上主人和一位同事的卡片，给同事写两条性格条目和一条"和主人的关系"。
- 加两件事（记忆），再加一条知识"登山团体"（长期任务），把那两件事挂到它下面。
- 把 `environment` 里的工作背景抄成一条知识。
- 改一条、停用一条，看历史里新旧版本都在；人物条目上能看到"主人原版"一栏。
- 按人筛，看同事的卡片上汇总出了和他有关的记忆和知识。
- 两个页面同时改同一条，后提交的那个应该看到"已被改过"的提示。
- "声纹标注"标签显示 0 条，结构说明可以展开看。

**算失败：**

- 改一条之后旧版本不见了，或者旧版本的内容被改了。
- 页面上显示的和数据库里的对不上（任意抽 5 条，直接查库核对）。

### 4.3 第 4 期：每日回顾与声纹标注（标注免费；做声纹要改耳朵）

用户回答第 4 条："声纹可以采用后标记方式，我们做一个前端，回顾每日时，顺便标记一下声纹，反正服务器有 opus 数据。"这一期取代第 2 版的无监督聚类试验。

#### 4.3.1 回顾页显示什么

一天一页，按时间往下排：

- **每句话**：时间、文字（SenseVoice，有听悟的同时显示听悟的）、长度、耳朵当时的判断（`known` / `unsure` / `unknown` 和最像谁、分数）、听悟的说话人编号、那一刻镜头里 M12 认出的名字。
- **播放**：点一下，服务器按这句的 `session` 和 `pos` 从 `audio.opus` 里切出这一段（前后各留 0.25 秒）发给页面播放。做法和现有的"最新画面"接口从录音目录读 JPEG 一样（`server/mind/api.py` 的 `/frames/latest`）。解码工具服务器上已有，审计用过【已核，审计附录】。
- **分组**：同一次连接里，听悟同一个说话人编号的连续句子默认折成一组，可以展开。
- **筛选**：只看 ≥1.5 秒的句子；只看还没标的；跳过 hello 自己出声的（`self` 标记）。
- **顺便回顾**：同一页上还能看当天的纪要和情景段。以后第 5 期的整理候选也放在这一页，主人回顾一天时一起过。

#### 4.3.2 怎么标、怎么存

- 每句（或每组）给几个按钮：选一个已有的人、新建一个人、"不认识"、"好几个人"、"hello 自己"、"噪音"、"听不清"。选人的列表来自 `people_cards`，新建的人同时建一张卡。
- 键盘快捷键：数字键选最近用过的几个人，空格播放，回车下一条。
- 每一下都写一条 `voice_labels`（结构见 3.1）。按组标时展开成每句一条。
- 耳朵当时的判断只是显示给主人参考，主人不点就不存。
- 改主意就再标一次，以最后一条为准。

#### 4.3.3 标注以后怎么用来认人

1. **算向量**：只给标过的句子算声纹向量，从 Opus 现算，写进可重算的 `voice_emb`：`{session, speech_id, model, pipeline: {denoise, version}, emb, dur}`。标过的句子不多，算起来很快。不需要改耳朵去存每句的向量。
   - 要记下流程版本：现在没有部署降噪，哪天部署了，向量就换了一个域，不能和以前的混在一起。
2. **给每个人做声纹**：用他标过的、单人、≥1.5 秒的句子。
   - 一个人可以有几条声纹，按录音条件分（机身麦克风、Mac 麦克风，或者离得远近）。主人那两条只有 0.348 的声纹很可能就是这个原因。
   - 先在服务器离线做，不碰耳朵。
3. **检验**：留出几天的标注不用来做声纹，专门检验：
   - 认出率：标为某人的句子里，有多少到了 `known`；
   - 认错率：标为 A 的句子被判成 B 的比例；
   - 两个门限 0.6 / 0.4 要不要按人或按录音条件调。
4. **放进耳朵**：检验通过后，经耳朵的一条新消息"加入这个声纹"由耳朵自己保存。不从外面写文件（1.2 节）。这是耳朵协议的改动，要和遥控方案改耳朵的部分排在一起上线，因为耳朵每重启一次当前连接都会断。
5. **以后**：标注攒得多了，可以训练更好的判别方式（不只是和平均向量比余弦）。这次不设计，只保证标注和录音位置都在，以后随时能重来。

实时"刚才是谁说的"仍然只靠耳朵的 `known`。回顾和标注是事后的工作，帮的是以后的认人。

#### 4.3.4 能试什么、怎么算失败

**能试**：打开昨天的回顾页，花十分钟听着标几十句；然后看"某人"的声纹做出来以后，留出那天的认出率和认错率是多少。

**算失败**：
- 点播放听到的不是那句话（位置对不上）。只要有一句对不上，就先查位置换算。
- 标一句平均超过 5 秒（主人觉得太累）。
- 检验时认错率超过 2%。
- 加入耳朵后，现场主人的 `known` 比例比加入前低。

### 4.4 人脸

- 围观模式不登记访客的脸（用户定）。
- 登记熟人的脸走模式设计 S7 的流程（"记住我的脸"，中文名字确认后下发 `learn`，名字进人物卡的 `links.face_names`）。本设计不另做。

## 5. 记忆和知识以后怎么长

### 5.1 第 2 期：身世年表（免费，规则生成）

- 从 `sessions`、`utterances`、`mind_runs` 用规则生成记忆 `self_event`：刷了新版本、启动、断线重连（同一启动号下的多个会话）、没播成的台词。
- 能免费得到的只有这些。没有重启原因，没有舵机、麦克风的记录，没开感官的启动看不到。
- 【我定】按事件生成，一件事一条。当天的条目在当天结束后才定稿，之前只显示、不落版本，免得每 10 分钟出一个新版本。
- 13 个没关上的会话是服务器侧耳朵重启，标成"服务器"，不算 hello 自己。
- 同时做两件让读取更快的免费小事：给 `sessions` 的时间字段加索引；点击路径不读 12 小时的纪要。

**能试**：页面上看"hello 的身世"，按天看刷了几个版本、重连几次。

**算失败**：11-08 至 11-12 每天的版本数、启动数和直接查 `sessions` 数出来的不一样；或者同一件事每 10 分钟多一个版本。

### 5.2 第 5 期：整理和融合（第一次花钱）

用户回答第 1 条："是记忆的提取融合和整理。"所以这一期是知识库真正长起来的地方。这次只定输入输出和规矩，融合方法设计时另写。

**每天一次整理**（借 generative agents"把观察归纳成更高层的结论"的思想；原文按重要性累积到门限就反思，每天两三次；"每天一次"是我的取舍【我定】）：

1. **提取**：从前一天的原话（只算 SenseVoice，每天约 1.5–2 万字）、纪要终版、陪伴和对话记录里，挑出值得长期留的事，写成记忆候选。原话必须进，因为纪要里没有听错的写法，也没有"谁被叫作什么"。
2. **融合**：把新记忆和意思相近的已有知识、人物条目放在一起，产出新版本或新条目，带完整来历（3.3）。找"意思相近"要用按意思检索（第 8 节）。
3. **整理**：长期任务的现状、地点、工作背景按新的事改写；过时的关掉（`valid_to`）；行话补 `heard_as`。

**规矩**：

- 引用必须存在，校验方式照抄现有记忆提取（`server/mind/memory_worker.py:89-121`）。
- 主人写的版本不改，只在后面追加。
- 依赖纪要开关。它现在关着，库里只有两天的纪要。纪要关着的日子，整理只读原话。
- 费用：约 0.03–0.06 美元一天【估算，含原话】，加上融合，留一个每天 0.2 美元的上限。
- 什么时候跑：见第 7 节。

**能试**：第二天打开感官后，回顾页上出现昨天的记忆候选和知识的新版本；每条知识能并排看主人原版和融合版，能点开它用到的那些记忆。

**算失败**：
- 融合版说不出来历（`derived_from` 为空，或者指向不存在的东西）；
- 主人原版被改了；
- 同一件事在知识里出现两条（融合没找到已有条目）；
- 主人读后认为三分之一以上的融合版不如原版；
- 任何一次整理在感官关着时跑了。

### 5.3 以后：连续剧、梗、情绪规律

这些是脱口秀和遥控方案要的，按用户方向往后放，只留接口约定：

- **连续剧**（跨天的同一件事）、**梗**（可以再提的一件事）：做的时候加成记忆的新种类。梗先只收主人点过的【我定】；"好"台词不自动等于梗。
- **使用记录**：脱口秀每轮要记下给了哪几条记忆、用了哪条（`memory_uses`），冷却和"被打坏就退场"靠它。要和脱口秀设计约定，加在 `say_rounds` 里。
- **口味**：归脱口秀设计的 `say_taste`，本设计不存第二份。
- **情绪规律**（"什么情况下主人常把 hello 调成什么样"）：等遥控方案的锚点落地，作为知识 `life` 由融合产出。到时补任务、开关和费用；检查的是这些句子本身（主人读后同意几成），不是遥控方案的影子预测。
- **翻旧账的分寸**：到做梗的时候再问。

### 5.4 模式接进来以后

模式会慢慢做，库不等它们。做到哪一个，就按下面的约定接：

- **陪伴**：情绪内容写成记忆 `feeling`，`source.kind = "companion"`，全局可用（用户回答第 2 条）；这个人亲口说的计划和约定写成记忆 `event` 或 `told`，以后由融合整理进知识和人物条目。陪伴的前提是先有这个人的卡（模式设计 5.7 节）。
- **对话**：读人物卡、人物条目、记忆和知识。
- **设置**：可以改人物卡，录人脸后写 `face_names`。
- **围观**：什么都不读，不登记脸。
- **脱口秀**：以后读，按人物卡的 `treatment` 过滤。

## 6. 知识库

按用户回答第 1 条，知识库是"综合的"，"包括生活中的事情"，是"记忆的提取融合和整理"。第 2 版里的"一本词典加 hello 的说明书"只是它的一小部分。

- **和记忆的界线**：记忆是一件件的事，带时间和出处；知识是从许多件事整理出来的结论，带"从哪些事来"（2.1）。
- **种类**：`place`、`work`、`commitment`、`life`、`term`、`self`、`other`。种类是可以加的词表。
- **第 1 期**：主人手写。最现成的第一批是 `environment` 里那 348 字，和主人知道的生活中的事。
- **第 5 期**：融合产出新版本（5.2）。
- **行话纠错**是知识的一种用法：纪要、mind、台词的提示里加一小节"可能听错的词"，只放这次输入里命中了 `name`、`aliases`、`heard_as` 的条目，用字符串匹配。
- **热词**：听悟有热词表功能。SenseVoice 在 sherpa-onnx 里据第三方说明不支持热词。同步热词会让原始转写依赖知识库的版本，回放对比变难。都是二手说明，暂不做。

**能试**（第 5 期以后）：在 11-11、11-12 的纪要上抽 30 处命中"可能听错的词"的地方，主人判断纠正得对不对；再抽 10 条融合出的知识，主人判断对不对、有没有重复。

**算失败**：主人否掉三分之一以上；或者纠错让纪要变差。

## 8. 按意思检索和图

**第 1 期不要。** 主人手填几十到几百条，按人、按时间、按种类、按知识条目取，都有索引。

**第 5 期要**，原因是用户回答第 1 条：知识要从全部数据里融合，融合前得先找到"意思相同的已有条目"，光靠字符串匹配会重复建。以后对话模式里"上次说的那个地方"这种问法，也要按意思找。

**做法**【我定】：

- 单独一个集合存文本向量：`{c, id, version, model, vec}`。不放进条目的版本里，这样换模型只要整批重算这个集合，不碰条目。
- 进程里用 numpy 暴力算。几千条只要几毫秒，不加向量数据库。
- 查询那句话也要先变成向量。优先在服务器本机装一个小的中文向量模型，免费，也不违反"关了不花钱"【假设：CPU 够用，没测】。退路是调付费接口，那就要守第 7 节的规矩。
- **什么时候改成别的做法**：同一场景下 `active` 的记忆加知识超过约 5 万条，或者暴力算超过 50 ms。到那时再比 FAISS 这类本机索引。

**图数据库以后也不打算要。** 人、知识、记忆之间就是几个编号数组（`subjects`、`topics`、`derived_from`）。

**声纹向量是另一回事**：它是从标过的句子算出来做认人用的，第 4 期才有，见 4.3.3。

## 10. 现成的项目：用不用

用户现在说的内容（事件、地点、背景、长期任务、从记忆里融合出知识）正是这些框架的本行。审计核对过的说法已更正。

| 项目 | 是什么 | 结论 | 理由 |
| --- | --- | --- | --- |
| **Mem0** | 从对话里抽事实，和已有的合并，存进向量库 | 第 1 期不用；**第 5 期设计融合时认真评估** | 它做的正是"提取加融合"。它支持 Qdrant、Chroma、FAISS 等二十多种向量库，不必用这台 MongoDB（第 1 版说"跑不了"是错的）。要看的是：它按"一个用户"设计，不分多个说话人；每次写入都调模型；现行文档写的是只增不改。 |
| **Letta / MemGPT** | 常驻的记忆块加可检索的档案，由智能体自己用工具改 | 第 1 期不用；对话模式做的时候再看 | pip 安装默认用 SQLite，不一定要 Postgres（更正第 1 版）。有了对话模式，"智能体自己改记忆"就和 hello 相关了 |
| **Zep / Graphiti** | 带有效期的知识图，矛盾时关旧开新 | 不用 | 要一个图数据库服务；每次写入都调模型和嵌入模型。借：知识的 `valid_from / valid_to` 加"矛盾时关旧开新" |
| **LangMem** | 语义、情节、做法三种记忆，后台整理 | 第 5 期一起比 | 核心接口可以接任何存储（更正第 1 版说的"绑在 LangGraph 上"）。它的"情节记忆 / 语义记忆"正好对应这里的记忆 / 知识 |
| **Cognee** | 把资料切块、抽实体建图 | 第 5 期一起比 | 默认三个嵌入式存储（SQLite、LanceDB、Ladybug，后者是 Kuzu 改名），不会多出一个数据库服务（更正第 1 版） |
| **Generative agents**（Park 等 2023） | 观察进一条流，重要性累积到门限就反思 | 借思想 | 原文按重要性之和超过门限触发，每天两三次。"每天一次"是我的取舍，不挂在论文名下 |
| **xiaozhi 的记忆模块** | 每个角色一段 JSON，每次对话后让模型重写 | 不用 | 不分人，没有证据和版本。项目已定 xiaozhi 只作参照 |
| **3D-Speaker / sherpa-onnx 的声纹** | 耳朵已经在用的声纹模型 | 第 4 期继续用 | 缺的不是模型，是标过的句子。sherpa-onnx 的聚类接口服务器上能直接用，但这次不做无监督聚类 |

结论：第 1 期是"建库加页面"，没有提取、没有检索，没有一个框架能省掉这部分工作。第 5 期设计融合时，Mem0、LangMem、Cognee 一起按当时的量重新比一次，能借就借。
