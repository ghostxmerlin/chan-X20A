# 图库：按时间管理、彻底删除机器人照片（设计）

2026-11-20 · 主人提出，Opus 起草

## 为什么

总会有些照片不适合留在服务器上。主人要一个自己能管理的界面，按时间找到这些照片并删掉。
删除的目的是**让那个画面从服务器上消失**，所以不能只删 jpg。照片的内容还以文字的形式写进了好几处，
这些地方都要清掉。

## 目标 / 不做 / 失败标准

- 目标：在 8787 控制台里按日期和小时翻看机器人身体摄像头的照片，可以单张删、多选删、整分钟删、整小时删；
  每次删除都把这张照片和由它产生的文字一起删掉。
- 不做：Mac 那台身体的照片（hello_mac，以后再加）；M12 的人脸事件（`vision` 表里只有框和名字，没有图片）；
  自动删除和定时清理（只删主人点过的）；回收站或撤销。
- 失败标准：删完之后，从服务器上的任何文件、任何表、任何页面还能读到那张照片，或者读到专门描述它的文字。

## 做法（主人已选定）

讨论过的三种删法：

1. **彻底删（主人选定）**：照片文件、frames 记录、"看一眼"记录、分钟描述，加上下面列出的所有衍生文字。没有回收站。
2. 回收站：可以救回误删，但清空之前照片还在服务器上，违背删除的目的。
3. 只删照片：描述照片的文字还留着，同样违背目的。

衍生文字一并删除（主人选 A）：被删照片所在分钟的**情景**，以及时间上与这些分钟重叠的**段落总结**，
整条删除。这段时间听到的总结会一起没掉，但原始录音和逐句文字保留。

## 一张照片会写进哪些地方（删除时全部清掉）

一张照片对应 `hello.frames` 里的一条记录，`path` 指向 `~/soul-spike/recordings/frames/<日>/<连接>/<t_us>-<seq>.jpg`。

| 地方 | 关联方式 | 删除时怎么处理 |
|---|---|---|
| jpg 文件 | frames.path | 删除文件（先校验真实路径在 recordings/frames 之内）；文件夹空了就一起删 |
| `frames` | 本身 | 删除记录 |
| `vision_looks`（看一眼，含千问回答） | path 相同 | 删除记录 |
| `eye_minutes`（每分钟描述） | frames[].path 包含这张照片 | 删除这一分钟的整条记录 |
| `mind_packages` | minute 相同，package.eye 里有描述 | 删除这一分钟的记录（各 lane） |
| `mind_scenes`（情景） | minute 相同 | 删除这一分钟的记录（各 lane） |
| `mind_segments`（段落总结） | [start, end) 与这一分钟重叠；end 为空表示还在进行 | 删除整条记录 |
| `mind_runs`（情景调用的请求和回答） | minute 相同 | 删除记录 |
| 运行日志 `log_YYYYMM` + `logbody_YYYYMM` | 这一分钟的 `call.eye` / `call.fusion`、这张照片的 `call.look`、被删段落的 `call.segment` | 删除日志行；正文没有别的行引用才删（正文按内容去重共享） |
| 其他日志正文（如实时语音的上下文） | 含被删文字的片段 | 片段替换成「［图库已删除］」 |
| 服务器 `~/soul-spike/log-spool/*.jsonl` | 含被删文字的片段 | 原地用等长 `*` 覆盖（文件大小不变） |

2026-11-20 核实：mind_state、notes_state、chat_turns、realtime_turns、conversations、memory_items 里没有找到描述原文。
删不到的：hello 说出口的话里对画面的转述（不是原文，无法可靠识别）；Mongo 托管方自己的备份。

## 页面（8787 新页「图库」，从 index.html 进入）

沿用 log.html 的风格（log.css 的颜色和字体变量），三栏布局：

```
┌ 日期 ──────┬ 20:00–21:00 ─────────────────────┬ 预览 ──────────┐
│ 11-20  4.1k│ 20:16 ▢▢▢▢▢▢▢▢  20:17 ▢▢▢▢▢      │  [大图]        │
│ 11-19  6.3k│ 20:18 ▢▢▣▣▣▢▢   20:21 ▢▢▢▢▢▢▢    │  20:18:07       │
│ 11-18  …   │ 每小时一条，可整小时 / 整分钟选中 │  看一眼：千问… │
│            │ [已选 3 张]           [删除所选]  │  [删除这张]    │
└────────────┴──────────────────────────────────┴────────────────┘
```

- 左栏：日期列表和每天的照片数；选中某天后显示 24 个小时，每小时标出照片数。
- 中栏：选中小时的缩略图，按分钟分组。点一下选中，Shift 点选一个范围；每组的分钟标题可以整组选中，
  小时标题可以整小时选中。照片多，缩略图按需加载，只加载能看到的那些。
- 右栏：大图、时间、连接、是不是快拍；如果被"看一眼"用过，显示千问的回答，并标出这一分钟有没有分钟描述和情景。
- 删除：确认框写清要删多少张照片、多少条看一眼、多少分钟的描述和情景、哪几段段落总结（列出标题），
  并说明删除后无法恢复。删完后页面就地移除这些照片，并显示实际删了多少。
- 名称都用中文（图库、看一眼、分钟描述、情景、段落总结），表名只用灰色小字标注。

## 维护时停机（主人 2026-11-20：维护时可以停机）

删除只在**维护状态**下进行，这样删的时候没有新照片进来，也没有服务在写分钟描述、情景和段落，不会删到一半又被写回去。

- 维护状态 = 机器人没有连着（没有新照片上传）+ mind 处于暂停（不调用模型，不写情景和段落）。
- 页面顶部有「开始维护」按钮：机器人还连着时，提示先关机或断开；断开后，借用现有的暂停机制（mind/pause.py）
  加一个「维护中」暂停原因，把暂停打开。「结束维护」再把这个原因撤掉。
- 不在维护状态时，可以翻看照片，但删除按钮不可用，旁边写明原因。
- 不用 systemctl 停服务：这些服务都是 systemd-run 临时启动的，一停就没了，要手工重建（见服务器重启恢复的记录）。
  所以"停机"是让它们空转，不是关掉进程。
- 删除清单的 plan_fp 校验保留，作为维护状态之外的第二道保险。

## 接口（放在服务器上的 mind 服务，8787 转发）

mind 已经能读 frames 表和照片文件（`/frames/latest`、`/looks/frame`），复用它的数据库连接和路径校验：

- `GET /gallery/days`：每天的照片数。
- `GET /gallery/hours?day=`：这一天每小时的照片数。
- `GET /gallery/frames?from&to`：一个时间段里的照片列表，带"看一眼 / 分钟描述 / 情景"标记，不含图片内容。
- `GET /gallery/image?id=&size=thumb|full`：一张图片。
- `GET /gallery/maintenance`：维护状态（机器人是否连着、是否暂停、暂停原因）；`POST /gallery/maintenance {on}`：开始 / 结束维护。
- `POST /gallery/plan {ids}`：返回一份删除清单（各处各删多少、段落标题），只读，供确认框使用。
- `POST /gallery/delete {ids, plan_fp}`：按清单执行删除；plan_fp 和当前清单对不上（期间有新数据）就返回 409，
  页面重新拉清单。每次最多 500 张（mind POST 正文上限 16 KiB），更多就由页面分批。返回每一处实际删了多少。

8787 的 server.mjs 把这几个路径加进转发白名单。写入照旧只接受来自本页的 JSON 请求。

mind 接口文件头那句"POST 不写原始记录"要改成：图库的删除接口例外，而且只做删除。

## 记录删除这件事

每次删除写一条运行日志 `gallery.delete`：时间范围、各处删除的条数、谁删的（page）。
**不写**照片路径和描述原文，否则日志本身就又成了一份副本。

## 留给实现者

- 缩略图的做法（服务器实时缩小，或者直接发原图让浏览器缩小；原图只有 320×240、约 5 KB，可以直接发原图）。
- 删除的执行顺序（建议先删文字和记录，最后删文件，这样中途失败也不会留下没有文件的孤立记录），以及中途失败时的处理（返回已删和未删，可以重试）。
- 测试：一个有 frames、looks、分钟描述、情景、段落总结的小测试库，删除后逐表核对；本地用 `.tools/ear-test-venv` 跑，不在服务器上跑。
- 部署：`server/mind/deploy.sh` 和 8787 重启。
