# hello 运行与审计日志：设计

日期：2026-11-16 · 状态：待主人审阅 · 范围：只含 hello 自己的服务器部分（ear / mind / eye / notes / memory / tts）

## 1. 为什么做

11-15 晚上 hello 掉线、11-16 一笔不明出图费用，两次都只能翻散落的文字日志和多张业务表去猜原因。主人要的是：服务器上 hello 的**一切运行和业务调用都留下有结构、可查询、可审计的记录，入库**，以后既能自己在网页上翻阅，也能写脚本深挖。

"运行日志"不只是系统状态，**业务调用本身也是运行日志**。

## 2. 目标

要记下的（主人原话归纳）：

**业务调用**（每次都要有：送进去的、得到的、模型、花费、耗时）
- 视觉：每一次识图的结果，包括每分钟识图（eye）、视觉爆发的每一张（look）。
- 情景（mind fusion / segments）和纪要（notes）：每次的输入和结果。
- 围观（realtime）、对话（chat）、脱口秀（say / round / prefetch / auto）：**系统输入**（提示词、背景、说明）、**用户输入**（听到的话）、**结果**。
- 其余付费或模型调用照此记录：长期记忆整理、听悟、soul-tts 合成、联网搜索。

**运行**
- 连接：机器人每条链路（hearing / mouth / vision / signal 等）连上、断开、原因。
- 开关：谁、从哪里（口令 / 数字 / 页面 / 开机 / 规则）、何时、改了哪个开关、改前改后。
- 触发：口令、数字、模式切换、预设、自动规则，每次怎么触发、结果是放行还是被拦（含围观"嗯"过滤、补救、先看再答、垫话、静音等回答闸门的每一次判定）。
- 费用：每一笔，可汇总成总账。
- 报错、服务起停、部署（代码版本）。

**使用方式**：网页上翻阅、筛选、点开看全文；脚本按统一格式查询。

## 3. 非目标

- 不记邻居项目（aidea、dojoagents 等），也不做整机体检（主人定：只包括 hello）。
- 不把照片、录音复制进日志（原件已永久保存，只记位置）。
- 不补建过去的历史（从上线起记；过去的数据仍在原业务表里）。
- 不和服务商账单自动对账（先把自己的账记准，对账以后再说）。
- 不替代现有业务表（`realtime_turns`、`vision_looks`、`mind_runs`……照旧给功能用，不改不删）。

## 4. 反目标（做到了也算失败的情况）

- 日志拖慢或弄坏 hello：任何写日志的失败、变慢，都不能让回答变慢、链路断开、服务退出。围观回答闸门在毫秒级路径上，写日志只能是"丢进队列就走"。
- 日志悄悄缺失：库连不上时把记录丢了却没人知道。审计日志必须能看出"哪里断了档"。
- 日志本身花钱：写日志不得调用任何付费服务。
- 日志泄露密钥：令牌、API 密钥、密码一律不进日志（家人和孩子的对话内容会进，这是主人要的；页面仍只走现有带令牌的监控）。
- 库被撑爆、索引吃掉共享 Mongo 的内存（Mongo 全机共用，常驻约 9.5 GB，11-15 晚刚出过内存事故）。

## 5. 约束（现状）

- Mongo 6.0.19，库 `hello`，全机共用一个 mongod。hello 库现有约 172 MB 数据（10 天），最大的是 `mind_runs`（约 10 KB/条）。硬盘剩 794 GB。
- 现有写库方式：`server/ear/hello_db.py` 用一个后台线程 + 有界队列，库断了只丢行（计数）。审计日志要比这更严（见 7.6）。
- 模型调用的汇聚点：mind 侧几乎全部经过 `mind/llm.py` 的 `chat()`（eye、fusion、notes、speak、chat、model_calls 都用它）；ear 侧是 `realtime_link.py`（DashScope realtime WebSocket）、`tingwu.py`、`vision_burst.py` 的 `dashscope_look`；soul-tts 是独立服务（源码在 `voice/tts_service/soul_tts`，部署到 `~/soul-tts`）。
- 开关和模式的写入点：mind `runner.py` 的 `set_switch / set_mind`、`mode_store.py`（已有 `mode_log`）、`billing.py` 预设、`api.py` 的 `/switches`；机器人那一半的开关在固件里，只能通过它上报的消息看到。
- 价格表：`mind/llm.py` 的 `PRICES`（美元，按 token）；围观用人民币估算；听悟按音频分钟。花费都是**按标价估算**。
- 密钥在服务器 `~/soul-spike/hello.env`（11-16 起 hello 独立）。
- 页面：本机网页监控（`web/monitor/`）经 mind API 转发，有两道放行名单（`server.mjs` 和 `mind.mjs` 的 PATHS / PARAMS）。

## 6. 方案比较

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **一、统一流水账（选定）** | hello 库新建统一日志，所有事件和调用同一格式写入；同一件事用链路编号串起来 | 查询只有一个入口、一种格式；代价是部分内容和业务表重复存 |
| 二、沿用业务表补缺 | 补开关历史、连接、费用总账等几张表，页面去拼十几张表 | 不重复存，但格式各异、提示词大多没存，脚本难写，补起来最零碎 |
| 三、现成工具（Langfuse 等） | 专门记模型调用的开源工具 | 自建要 ClickHouse / Redis 等一整套，压在刚爆过内存的共享机器上；用云服务会把家人对话送到外面；也只管模型调用，连接 / 开关 / 触发还得另做 |

主人选定方案一，并要求考虑数据量和表大小；随后同意：**分成"流水"和"正文"两层、正文去重、按月分表、永久保留**。

## 7. 设计

### 7.1 两层

- **流水（flow）**：每件事一条小记录（几百字节），只放信封和用于筛选的摘要。只有这一层建索引。网页翻阅、筛选、脚本统计都只扫这一层。
- **正文（body）**：提示词、背景、输入、输出的全文。按内容哈希（sha256）去重，同样的内容同一个月只存一份；只按编号取，除主键外不建索引。流水用 `body` 字段引用正文编号。

### 7.2 按月分表、永久保留

- 表名：`log_YYYYMM`（流水）、`logbody_YYYYMM`（正文），按北京时间（Asia/Shanghai）划月。
- 正文去重只在同一个月内：跨月同一段提示词各存一份，换来每个月的表彼此独立、旧月份可整体冷放。
- 永久保留，不自动删、不自动压缩归档。旧月份照常可查，只是不常用、不常驻内存。
- 写入方第一次写某个月时建好该月的索引。

### 7.3 流水记录的格式（信封）

每条都有：

| 字段 | 含义 |
| --- | --- |
| `at` | 毫秒时间戳（服务器墙钟） |
| `svc` | 哪个服务：ear / mind / eye / notes / memory / tts |
| `kind` | 类型，点分层级，如 `call.realtime.turn`、`gate.realtime`、`switch.set`、`link.open`（清单见 7.4） |
| `trace` | 链路编号：同一件事的各步共用（见 7.5） |
| `seq` | 本服务进程内递增序号；配合 `run`（本进程启动编号）判断有没有断档 |
| `run` | 服务进程启动编号（每次启动新生成），起停事件里带代码版本 |
| `ok` | 成功 / 失败；失败时 `err` 一句话 |
| `ms` | 耗时（有的话） |
| `model`、`usage` | 模型名、服务商原样返回的用量（token、音频秒数、字符数……） |
| `cost` | `{amount, cur: "USD"|"CNY", est: true, basis}`：估算金额、币种、依据（价格表版本）；不花钱的事件没有这个字段；价格未知时 `amount: null`，用量照记 |
| `key` | 这次调用用的密钥指纹（开头 7 个字符，如 `sk-xTVl`），用于和服务商账单对照；从不记完整密钥 |
| `by` | 谁触发的：asr / digit / page / boot / rule / robot / mind / timer…… |
| `mode` | 当时 hello 的模式 |
| `sum` | 一行中文摘要（例如听到的话前 60 字、回答前 60 字、开关"听悟 开→关"），给页面列表和简单筛选用 |
| `body` | 正文引用：`{system, context, input, output, …}` → 正文编号；没有大段内容时省略 |
| `ref` | 指向原件或业务表：录音 `session` + `pos`、照片路径、`realtime_turns.tid`、`mind_runs` 的 id 等 |

小内容（几十字的听到的话、一句回答）直接放 `sum` 也放正文，保证脚本只靠日志表就能拿到全文。

### 7.4 记录点清单（类型）

- **服务**：`svc.start`（代码版本、参数摘要，不含密钥）、`svc.stop`、`svc.beat`（每分钟一次心跳，带本分钟各类计数）、`svc.error`（未处理的异常、调用报错）。
- **连接**：`link.open` / `link.close`（ear 每条机器人链路：哪条、boot、对端、时长、原因），`link.upstream`（ear 到听悟、realtime、soul-tts 的上游连接起落）。
- **开关 / 模式 / 预设**：`switch.set`（名、改前、改后、by、成功与否）、`mode.change`、`preset.apply`（数字、各步结果）、`billing.set`。机器人一半的开关，按它上报的消息记 `robot.state`。
- **触发与闸门**：`trigger.*`（口令词、数字、双击、视觉爆发启动词……：识别到什么、结果）、`gate.realtime`（每次回答闸门判定：放行 / muted_quiet / muted_unclear / muted_repeat / muted_blind / muted_wait_look / rescue……及理由）、`filler.play`。
- **业务调用**（每次一条，正文里存系统输入 / 背景 / 用户输入 / 输出全文）：
  - `call.eye`（每分钟识图）、`call.look`（视觉爆发每张；照片记路径）；
  - `call.fusion`、`call.segment`（情景）、`call.notes`（纪要）；
  - `call.realtime.session`（会话开关、说明全文、背景每次更新）、`call.realtime.turn`（每轮：听到的转写、ear 自己的识别、回答转写、用量、花费、各段延迟）、`call.realtime.search`（触发联网搜索时）；
  - `call.chat`（对话每轮）、`call.say.*`（脱口秀各步）；
  - `call.memory`（长期记忆整理）；
  - `call.tingwu`（听悟任务起止、音频时长、花费）；
  - `call.tts`（soul-tts 每次合成：字数、声音、时长、花费）。
- **听到的话**：`heard.asr`（ear 本地识别的每句：文字、session、pos），它是"用户输入"的源头，链路从它开始。

各模块具体在哪一行挂记录点，由建造者对着代码定；原则是**挂在汇聚点**（`llm.chat`、realtime 的回合收尾、闸门判定处、开关写入处），不要散落。

### 7.5 链路编号

- 一件事从源头生成一个 `trace`，沿途各步沿用：听到一句 → 闸门判定 → realtime 回答 → 机器人播出；一次口令 → 预设 → 各开关变化；一次视觉爆发 → 每张识图；一分钟 → 情景 → 纪要。
- 跨进程（ear → mind）时，编号随现有消息 / HTTP 请求带过去（加一个字段，不改原有语义）。
- 网页点开任一条，按 `trace` 拉出整条链。

### 7.6 写入：不拖慢、不丢、能看出断档

- 每个服务用同一个小写入模块（放在 server 公共位置，ear 和 mind 共用；soul-tts 也是 hello 自己的项目，部署时把同一模块一起带过去），调用方只做"组装 + 丢进内存队列"，立即返回。
- **先落盘，再入库**（Claude 的决定，见第 9 节）：后台线程把每条记录先追加到本机磁盘的日志文件（按服务、按天的 JSON Lines，`~/soul-spike/log-spool/`），再由同一线程批量写进 Mongo，写成功后记下文件里的进度。进程被杀时，已落盘但没入库的记录在下次启动时补写；补写保持原 `at`、`seq`、`run`。库断了也一样，只是落盘文件积压，恢复后补写。
- 落盘文件入库后保留 7 天再删（排查用，库里才是永久的那份）。每天约几十 MB，硬盘无压力。
- 只有"已进内存队列、还没落盘"的那一瞬间（毫秒级）在进程被杀时会丢；能从 `seq` 跳号看出来。
- 队列满了（极端情况）只丢心跳；真丢了要在下一条心跳里记"丢了多少"。
- 每分钟心跳 + 每进程 `seq` 连续，查询时能直接找出断档（服务挂了、库断了、进程被杀）。心跳里带当前各开关状态，所以"开关关着、服务闲着"和"服务没了"能分开：前者有心跳、只是没有业务调用；故意停掉服务要记 `svc.stop`（原因：手动 / 部署），不算断档。
- 正文去重：写正文前按哈希查本进程缓存，已写过就只引用；缓存未命中时 upsert（同哈希重复写是安全的）。

### 7.7 索引（只建在流水表上，尽量少）

- `at`
- `kind` + `at`
- `trace`
- 部分索引：有 `cost` 的记录按 `at`（总账用）

其余筛选（服务、模型、by、模式）在时间范围内扫描即可。每月新表建同样索引。

### 7.8 数据量估算（按 11-15 全开一整天）

| 来源 | 每天约 |
| --- | --- |
| 情景 + 纪要（每分钟各一次，输入输出全文） | 30 MB |
| 识图（每分钟 + 视觉爆发，不存图） | 3 MB |
| 围观 / 对话 / 脱口秀（每轮输入输出、闸门判定） | 几 MB |
| 围观背景（约 30 秒更新，内容变才存新版） | 5 MB |
| 连接、开关、触发、心跳、费用 | 1 MB |

合计每天 40–60 MB 原始、压缩后 15–25 MB；一年 5–10 GB 盘上空间。流水层一年约 500 万条，只靠上面 3–4 个索引，按月分表后常驻内存的只有当月索引（预计几十 MB）。

### 7.9 读取：网页 + 脚本

- **mind 提供只读接口**（带现有令牌）：按时间 / 类型 / 服务 / 链路 / 有无花费筛选流水；按编号取正文；按天 / 服务 / 模型汇总花费。分页返回，单次有上限。网页监控两道放行名单都要加这些路径。
- **网页**（`web/monitor` 里新增一页）：
  - 时间线列表（时间、服务、类型、摘要、花费），顶部筛选；
  - 点开一条看信封 + 正文全文；点链路编号看整条链；
  - 总账：今天 / 选定日期，按服务、模型、币种分开合计；
  - 断档提示：某服务心跳缺失、`seq` 跳号的时段标红。
- **脚本**：仓库里提供一个查询小模块和一份格式说明（字段、类型清单、示例查询），脚本直接连 Mongo 读 `log_*` / `logbody_*`。

### 7.10 安全与隐私

- 写入模块统一过滤：键名含 key / token / secret / password / authorization 的值一律替换为 `***`；URL 里的查询串令牌同样处理。
- 正文里会有家人、孩子的对话：只存在 hello 库，只通过带令牌的 mind 接口和本机监控页面看；孩子的名字不进仓库（现有规矩照旧）。

### 7.11 服务清单

`svc` 取值和运行方式（都是常驻进程，开关关着时闲着、不退出）：ear（soul-spike）、mind（soul-mind）、eye（soul-eye）、notes（soul-notes）、memory（soul-memory，常驻，每天在安静时整理一次）、tts（soul-tts）。每个都有自己的 `run` / `seq` / 心跳。

## 9. 审稿后定下的（Claude 的决定，主人可改）

- **soul-tts 自己记**：它是 hello 的项目，直接改它，`call.tts` 和它的心跳由它自己写，字数、时长、花费都是实数。
- **先落盘再入库**（7.6）：审稿指出只在断库时落盘，进程被杀会丢掉最关键的最后几秒（11-15 那种情况）。改成每条先追加到本机文件，代价只是每天几十 MB 的写盘。
- **链路止于 ear**：ear 看到 `/mouth` 流结束就算"播出"，不改固件、不改机器人协议（固件归 codex-astra，以后要细到机器人再单独商量）。机器人一半的开关照它现有上报记 `robot.state`。
- **缺的价格自己查公开标价**：听悟（按音频分钟）、soul-tts 合成（百炼 TTS 按字数）、围观联网搜索费、记忆整理，按服务商官网 / aihubmix 当前标价填进价格表，每条记 `basis`（来源和日期）；查不到的 `amount: null`，用量照记，页面总账标"含未知"。
- **每条调用记密钥指纹**：11-16 的出图费其实是邻居 aidea 用同一把密钥花的。hello 已于 11-16 换成自己的密钥（`~/soul-spike/hello.env`），再在每条调用记指纹，以后账单上对不上的钱能一眼看出不是 hello。

## 10. 留给建造者的

- 各模块记录点的准确挂载位置和每类 `kind` 的具体字段。
- 写入模块的批量大小、队列长度、补写节奏。
- 页面布局和交互细节（沿用 `web/monitor` 现有风格）。
- 价格依据的表示方式（价格表版本号或日期）。
- 测试：写入模块的单测（去重、脱敏、断库落盘再补写、断档检测）；各记录点至少一条用例；用 11-15 的录音回放一次，看一天的记录量和表大小是否符合 7.8。
